# 선착순 한정 판매 MSA — 0단계 설계

- 작성일: 2026-10-29
- 범위: 0단계 (일부러 깨지는 기준 버전 + 측정 환경)
- 표기: **[사용자 결정]** 은 사용자가 정한 것, **[설계자 판단]** 은 대화 중 설계자가 정하고 사용자가 이의 없이 넘어간 것 또는 문서 작성 중 정한 것.

## 1. 의도와 이유

실제 배포 없이 로컬에서 MSA 이커머스를 만들고, 부하 생성 도구(k6)로 시나리오를 돌리면서 문제를 직접 재현하고 단계적으로 고쳐 나가는 **실험·학습 프로젝트**다. **[사용자 결정]**

첫 번째이자 당분간 유일한 시나리오는 **선착순 한정 판매**다. 오픈 시각에 다수의 사용자가 같은 상품을 동시에 구매하려고 몰리는 상황이다. **[사용자 결정]**

실패 기준은 하나다: **재고보다 많이 팔리면 실패.** **[사용자 결정]**

진행 방식은 "깨지는 버전부터": 0단계에서는 일부러 순진하게 구현해 초과 판매가 실제로 터지는 것을 부하 테스트로 확인하고, 이후 단계마다 해결책을 하나씩 적용해 같은 시나리오로 다시 측정·비교한다. **[사용자 결정]**

원칙: **한 번에 한 문제만 다룬다.** 동시에 두 문제를 풀면 집중 대상이 분산된다. 그래서 "1인 1개 구매 제한"은 초과 판매 로드맵 전체를 마친 뒤 별도 제약으로 추가한다. **[사용자 결정]**

## 2. 목표 / 비목표 / 안티 목표

### 목표 (0단계)
- 서비스 5개 + 게이트웨이가 Docker Compose 로 로컬에서 한 번에 뜬다.
- 명령 하나로 "데이터 초기화 → 시드 → k6 실행 → 정합성 검증 → 결과 기록"이 끝난다.
- 0단계(naive) 전략으로 돌리면 **초과 판매가 반복적으로 재현된다.** (0단계에서는 초과 판매가 "나는 것"이 성공이다.)
- k6 지표와 서비스 지표를 Grafana 한 화면에서 볼 수 있다.
- 재고 차감 방식을 **설정값으로 바꿔 끼울 수 있는 구조**가 처음부터 있다 (구현은 naive 하나만).

### 비목표
- 실제 배포, 실제 PG 연동.
- 장바구니, 배송, 리뷰, 쿠폰, 검색, 알림.
- 1인 1개 구매 제한 (로드맵 마지막에 별도로).
- 선착순 외 시나리오 (상품 조회 폭주 등).
- 1단계 이후의 해결책 구현 (Redis, Kafka, 락 등).

### 안티 목표 (기술적으로 돌아가도 이렇게 되면 실패)
- **0단계가 우연히 안전해지는 것.** 예: 조건부 UPDATE(`WHERE stock > 0`), `@Version`, `SELECT ... FOR UPDATE`, 유니크 제약을 무심코 써서 경쟁 조건이 사라지는 경우. 경쟁 조건은 진짜여야 한다.
- **다른 요인이 초과 판매에 섞이는 것.** 예: HTTP 클라이언트 자동 재시도로 이중 차감이 생기면 "락이 없어서"인지 "재시도 때문"인지 구분이 안 된다. 0단계에서는 원인이 하나(재고 조회 후 차감 경쟁)여야 한다.
- **단계 간 비교가 안 되는 측정.** 시나리오·데이터 규모·인프라 설정이 단계마다 달라지면 안 된다. 결과마다 사용한 설정이 함께 기록돼야 한다.
- 주변 도메인(회원, 상품)을 두껍게 만드는 것.

## 3. 제약

- 로컬 Mac 한 대에서 서비스·DB·모니터링·k6 를 모두 돌린다. CPU를 나눠 쓰므로 **절대 수치보다 단계 간 상대 비교에 의미**가 있다.
- 언어/프레임워크: **Java + Spring Boot** **[사용자 결정]**, 버전은 Java 25(LTS) + Spring Boot 4.x + 대응하는 Spring Cloud **[설계자 판단]**. 호환 문제가 있으면 빌더가 Java 21 + Spring Boot 3.5 로 내려도 된다.
- 부하 도구: **k6** **[사용자 결정]**
- 빌드: Gradle 멀티 모듈 **[설계자 판단]**
- 실행: Docker Compose **[설계자 판단]**. 서비스 디스커버리(Eureka 등) 없이 Compose 컨테이너 이름으로 호출.

## 4. 서비스 구성 [설계자 판단, 사용자 승인]

```
                 k6
                  │
             [Gateway]
     ┌────────────┼─────────────┐
  [User]      [Product]      [Order] ──▶ [Inventory]
                                │
                                └──────▶ [Payment(가짜)]
```

| 서비스 | 책임 | 비중 |
|---|---|---|
| Gateway | 외부 진입점, JWT 검증 후 하위 서비스에 사용자 ID 전달 | 얇게 |
| User | 회원 가입, 로그인, JWT 발급 | 얇게 |
| Product | 상품 정보, 선착순 행사 정보(오픈 시각, 판매 수량, 가격) | 얇게 |
| Inventory | 재고 수량 보관, 차감, 복구 | **핵심** |
| Order | 주문 생성, 재고 → 결제 → 확정 흐름 조율, 실패 시 재고 복구 | **핵심** |
| Payment | 지연 시간·실패율을 조절할 수 있는 가짜 PG | 중간 |

- Inventory 와 Payment 는 외부(게이트웨이)에 노출하지 않는 내부 서비스다.
- 재고를 Product 에서 분리한 이유: 오픈 순간의 읽기(조회)와 쓰기(차감)는 몰리는 방식이 달라 따로 개선하기 쉽고, 재고·주문·결제가 다른 서비스에 있어야 MSA 특유의 정합성 문제(복구 누락, 재시도 이중 차감 등)를 이후 단계에서 직접 겪어볼 수 있다.

### 데이터 저장 [설계자 판단]
- MySQL 컨테이너 **1개**에 서비스별 **스키마를 분리**한다 (user_db, product_db, inventory_db, order_db, payment_db). 서비스는 자기 스키마에만 접근하고, 스키마 간 조인 금지. 로컬 자원 절약 목적.
- Redis, Kafka 는 0단계에 띄우지 않는다. 필요한 단계에서 추가한다.

### 주요 데이터 (필드는 빌더가 다듬어도 됨)
- User: `users(id, email, password_hash, name, created_at)`
- Product: `products(id, name, price, ...)`, `flash_sale_events(id, product_id, open_at, sale_quantity, ...)`
- Inventory: `inventory(product_id, quantity)` — 행사 상품 1개당 재고 행 1개
- Order: `orders(id, user_id, event_id, product_id, quantity=1, amount, status, created_at)` — 상태: `PENDING`, `PAID`, `FAILED`
- Payment: `payments(id, order_id, amount, status, created_at)`

## 5. 0단계 주문 흐름

클라이언트가 `POST /api/orders { eventId }` 를 호출하면 Order 서비스가 **동기 REST** 로 다음을 수행하고 결과를 동기로 응답한다.

1. Product 에서 행사 정보 조회 (오픈 여부, 상품 ID, 가격). 오픈 전이면 거절.
2. 주문을 `PENDING` 으로 저장.
3. Inventory 에 차감 요청.
   - 재고 없음 → 주문 `FAILED`, 응답 409(품절).
4. Payment 에 결제 요청.
   - 승인 → 주문 `PAID`, 응답 성공.
   - 거절 → Inventory 에 복구 요청, 주문 `FAILED`, 응답 실패.

### Inventory 의 0단계(naive) 차감 — 초과 판매가 나는 지점
- 재고 행을 **락 없이** 읽고, 애플리케이션에서 `quantity > 0` 을 확인한 뒤, `quantity - 1` 을 계산해 그 값으로 저장한다 (JPA 엔티티를 읽어 값을 바꾸고 저장하는 평범한 방식).
- 동시에 들어온 요청들이 같은 수량을 읽고 같은 값으로 덮어써서 차감이 유실된다. 그 결과 재고가 0이 되기 전까지 판매 수량보다 많은 차감 요청이 "성공"하고, `PAID` 주문 수가 판매 수량을 넘는다.
- 복구(increase)도 같은 naive 방식으로 구현한다.

### 원인을 하나로 유지하기 위한 규칙 [설계자 판단]
- 서비스 간 HTTP 호출에 **자동 재시도 없음.** 타임아웃은 명시적으로 설정한다.
- **원격 호출을 감싸는 DB 트랜잭션 금지.** 각 서비스의 로컬 작업은 각자 짧은 트랜잭션으로 끝낸다.
- 타임아웃은 넉넉한 고정값으로 두고 결과에 함께 기록한다. Inventory·Payment 호출이 타임아웃이나 오류로 **결과를 알 수 없을 때**는 주문을 `FAILED` 로 두고 **재고를 복구하지 않는다.** 실제로 차감되지 않은 재고를 복구하면 그 자체가 초과 판매의 두 번째 원인이 되기 때문이다. (재고가 덜 팔리는 쪽으로 어긋나는 것은 0단계 실패 기준이 아니다.)
- Payment 기본값: 지연 약 200ms 수준, **실패율 0%.** (결제 실패·타임아웃으로 인한 정합성 문제는 4단계 주제다.)
- 가상 스레드(virtual threads) **끄기.** 톰캣 스레드 풀, Hikari 커넥션 풀 등은 기본값으로 두고, 바꾸면 결과에 기록한다.

### 전략 교체 구조
- Inventory 의 차감/복구 로직은 인터페이스 뒤에 두고, 설정값(예: `inventory.strategy=naive`)으로 구현을 고른다. 0단계는 `naive` 하나만 구현한다. 이후 단계는 구현체를 추가하는 방식으로 진행해, 같은 코드에서 여러 전략을 같은 시나리오로 나란히 돌려볼 수 있게 한다.

## 6. 인증 [설계자 판단]
- User 서비스가 로그인 시 JWT 를 발급한다.
- Gateway 가 JWT 를 검증하고 사용자 ID 를 헤더(예: `X-User-Id`)로 하위 서비스에 전달한다. 하위 서비스는 토큰을 다시 검증하지 않는다.
- 부하 테스트용 회원과 토큰은 **측정 구간 밖에서** 준비한다. 로그인 부하는 측정 대상이 아니다.

## 7. 부하 시나리오 (k6)

- 판매 수량 **100개**짜리 행사 1개.
- 테스트 회원 **수천 명**(기본 5,000명 제안, 환경변수로 조절)을 미리 만들어 둔다.
- 오픈 시각에 각 가상 사용자가 **서로 다른 회원으로 한 번씩** `POST /api/orders` 를 동시에 보낸다. 같은 회원이 연타하는 시나리오는 없다 (1인 1개 제한이 범위 밖이므로).
- 상품 조회 트래픽 등 다른 부하는 섞지 않는다.
- 수치(회원 수, 판매 수량, 동시성, executor 종류)는 환경변수로 바꿀 수 있게 하되, 한 번 정한 기준값은 단계 간 비교를 위해 고정한다.

## 8. 측정과 검증

### 지표
- Spring Boot Actuator + Micrometer → Prometheus → Grafana: HTTP 응답 시간, 처리량, 에러율, 커넥션 풀, JVM.
- k6 결과도 Prometheus 로 보내(remote write) 같은 Grafana 에서 본다.
- 컨테이너 자원 사용량·MySQL 지표 수집은 빌더 판단 (있으면 좋음).

### 실행 후 자동 검증 (매 실행)
- 판매 수량(초기 재고), `PAID` 주문 수, 최종 재고를 모아 출력한다.
- **초과 판매 수 = PAID 주문 수 − 판매 수량** (0보다 크면 FAIL).
- 재고 불일치 = (초기 재고 − 최종 재고) 와 PAID 주문 수의 차이 (참고 지표).
- 검증에 필요한 값은 각 서비스의 내부/관리용 API 로 가져온다 (서비스가 다른 서비스 DB 를 직접 읽지 않는다).

### 결과 기록
- 매 실행마다 결과 파일을 남긴다: 실행 시각, 전략 이름, 시나리오 설정값(회원 수, 판매 수량, 동시성), 주요 인프라 설정, k6 요약(TPS, p95/p99, 에러율), 검증 결과(초과 판매 수, 재고 불일치).
- 위치는 `docs/results/` 아래 (형식은 빌더 판단).

### 재현성
- 실행 전 주문·결제 데이터 초기화와 재고 리셋을 스크립트로 자동화한다.
- 명령 하나(예: `scripts/run-test.sh naive`)로 초기화 → 시드 → k6 → 검증 → 기록까지 끝난다.

## 9. 0단계 완료 기준
- `docker compose up` 으로 전체가 뜬다.
- 실행 스크립트 한 번으로 테스트 → 검증 → 결과 기록이 끝난다.
- naive 전략으로 **연속 3회 실행 시 3회 모두 초과 판매가 발생**한다.
- Grafana 에서 k6 지표와 서비스 지표를 볼 수 있다.
- 0단계 결과가 `docs/results/` 에 기록돼 있다.

## 10. 이후 로드맵 (이번 범위 아님, 단계마다 따로 설계)

| 단계 | 방식 | 확인할 것 |
|---|---|---|
| 1 | DB 수준: 비관적 락, 낙관적 락, 조건부 UPDATE | 정확해진 대신 얼마나 느려지나 |
| 2 | Redis 원자 연산으로 재고 관리 | DB 부하가 줄어드나 |
| 3 | 대기열 또는 Kafka 비동기 주문 처리 | 몰리는 순간을 평평하게 만들 수 있나 |
| 4 | 장애로 생기는 초과 판매: 결제 타임아웃·재시도 이중 차감 → 멱등키, 보상 처리 | 결제 실패율을 올려도 정합성이 유지되나 |
| 5 | 1인 1개 구매 제한 추가 — 다시 "깨지는 버전"부터 | 중복 구매 0건 |

## 11. 빌더에게 맡기는 것
- 포트, 패키지 구조, 정확한 API 경로와 DTO.
- 서비스 간 HTTP 클라이언트 종류(RestClient, HTTP Interface, OpenFeign 등) — 단, 자동 재시도는 끄기.
- Spring Cloud Gateway 의 WebFlux / MVC 변형 선택, JWT 라이브러리.
- 스키마 마이그레이션 도구(Flyway 등), 테스트 전략(Testcontainers 등).
- 공통 모듈을 둘지 여부 (두더라도 최소한으로).
- k6 executor 종류와 기본 동시성 수치, Grafana 대시보드 구성, 결과 파일 형식.
- 테스트 회원·토큰을 준비하는 방법 (단, 측정 구간 밖에서).
