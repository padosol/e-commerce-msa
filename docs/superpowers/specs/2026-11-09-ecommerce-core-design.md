# 선착순 MSA — 2단계 설계 (이커머스 기본 기능, DDD·헥사고날)

- 작성일: 2026-11-09
- 범위: 2단계. 상품 목록 → 장바구니 → 주문 → 결제 → 주문 내역까지 쓰는 이커머스 기본 흐름을 만든다. 다섯 서비스의 안쪽 구조를 DDD·헥사고날로 정리하고, 결제는 가짜 PG가 무작위로 실패하게 한다.
- 전제: 0단계 설계 `2026-10-29-flash-sale-msa-design.md`, 1단계 설계 `2026-11-01-flash-sale-stage1-design.md`, 그리고 그 구현(브랜치 `feat/flash-sale-stage1`). 여기 적지 않은 규칙은 앞 단계 그대로다.
- 표기:
  - **[사용자 결정]**: 사용자가 정한 것.
  - **[설계자 판단]**: 대화 중 설계자가 짐작으로 제시하고 사용자가 "그대로 진행"으로 넘어간 것, 또는 문서를 쓰면서 정한 것.

## 1. 의도와 이유

1단계가 끝난 뒤 로드맵의 다음 단계는 Redis 였다. 그런데 1단계 기록은 Redis 의 근거("재고 한 행에 몰리는 구조의 한계")를 뒷받침하지 않았다.
- 4차: 줄이 재고 행이 아니라 order-service 앞단에 섰다.
- 5차: 낙관적 락만으로도 재고 차감 서버 p95 가 4~6ms 였다.

그래서 사용자는 다음 단계를 **이커머스를 어느 정도 완성하는 것**으로 정했다. **[사용자 결정]**

"어느 정도 완성"의 범위는 사용자 흐름 하나다. 상품 목록 보기 → 장바구니에 담기 → 주문 → 결제 → 주문 내역 조회. **[사용자 결정]**

구조와 방식:
- **DDD·헥사고날 아키텍처로 구성하되, 복잡하지 않고 최대한 단순하게 한다.** **[사용자 결정]**
- **PG 는 가짜(fake) 구현체를 두고, 결제가 무작위로 실패하게 한다.** 테스트를 하기 위해서다. 실제 PG 는 나중에 다른 구현체를 끼워 넣는 방식으로 붙인다. **[사용자 결정]**
- 그래서 PG 는 포트(인터페이스) 뒤에 숨기고, 가짜 PG 는 그 포트의 어댑터 하나가 된다.

Redis 단계는 근거가 생길 때까지 보류한다. 로드맵의 나머지(대기열·Kafka, 결제 장애와 멱등성, 1인 1개 제한)는 순서대로 그 뒤에 남는다. **[설계자 판단: 사용자 결정을 로드맵에 반영]**

## 2. 목표 / 비목표 / 안티 목표

### 목표
- **사용자 API**: 상품 목록·상세, 장바구니(보기·담기·수량 바꾸기·빼기), 장바구니 주문, 내 주문 목록·상세. 화면은 만들지 않고 게이트웨이 뒤 REST API 만 만든다. **[설계자 판단]**
- **가짜 PG**: payment-service 의 결제 흉내 코드(`PaymentSimulator`: 지연, 지연 흔들림, 실패율)를 `PaymentGateway` 포트의 가짜 어댑터로 옮긴다. **[사용자 결정: 가짜 PG·무작위 실패 / 설계자 판단: 기존 흉내 코드 재사용]**
- **구조**: 서비스 다섯 개(user, product, inventory, order, payment)의 안쪽을 §4 의 패키지 구조로 정리한다. 서비스 개수와 나눔은 그대로다. **[설계자 판단]**
- **도메인 객체는 순수 자바로 둔다.** JPA 어노테이션을 붙이지 않고, 영속성 어댑터에 JPA 엔티티를 따로 둬서 서로 옮긴다. **[사용자 결정: A안]**
- **선착순 실험을 계속 돌릴 수 있게 둔다.**
  - 선착순 이벤트 주문, k6 측정 스크립트, 1단계 재고 전략 4개(`naive`, `pessimistic`, `conditional`, `optimistic`)와 전략 전환 방식을 유지한다. **[설계자 판단]**
  - 구현이 끝나면 1단계 5차와 같은 매트릭스를 다시 돌려, 판정이 그대로인지 확인한다(§8).

### 비목표
- 화면(웹 프런트엔드).
- 실제 PG 연동. 포트만 열어 둔다.
- 결제 재시도, 멱등키, 결제 결과를 알 수 없을 때의 보상 처리(로드맵 4단계).
- 주문 취소·환불, 배송, 쿠폰·할인, 검색·카테고리, 관리자 화면.
- 장바구니 일부만 골라 주문하기.
- 같은 장바구니를 동시에 두 번 주문하는 경우의 방어(이중 결제 방지는 4·5단계 주제다).
- 1인 1개 구매 제한(5단계), Redis, Kafka.
- 성능 튜닝. 고정 설정(컨테이너 한도, Tomcat/Hikari 기본값, 타임아웃)은 1단계 그대로 둔다.

### 안티 목표 (돌아가더라도 이렇게 되면 실패)
- **선착순 실험이 깨지는 것.**
  - `scripts/` 와 `load-test/k6/` 가 쓰는 API 의 경로·요청·응답이 바뀌면 안 된다. 바뀌어도 되는 것은 측정 스크립트를 같이 고친 경우뿐이다.
  - 해당 API: `POST /api/orders`(eventId), `/internal/*` 의 이벤트 생성, 재고 설정·조회, 통계, 초기화, 전략 조회, 결제 설정.
  - 판정 규칙(`scripts/verdict.jq`)이 같은 결과를 내야 한다.
- **naive 가 조용히 안전해지는 것.** 구조를 옮겨도 `NaiveStockStrategyTest.concurrentDecreasesLoseUpdates` 는 계속 통과해야 한다. 공용 재고 JPA 엔티티에 `@Version` 을 붙이지 않는다.
- **도메인이 바깥 기술을 아는 것.** `domain` 패키지가 Spring, JPA(`jakarta.persistence`), 웹, HTTP 클라이언트에 의존하면 실패다.
- **단순하게 하라는 요청을 넘어서는 구조.** 다음은 이번 단계에 넣지 않는다.
  - CQRS, 이벤트 소싱, 도메인 이벤트 버스
  - Gradle 모듈 분리
  - 유스케이스마다 인바운드 포트 인터페이스
  - 공통 베이스 클래스·공용 라이브러리 모듈
- **초과 판매나 재고 누수의 새 원인이 생기는 것.**
  - 결제 거절(결과를 아는 실패)이면 차감한 재고를 모두 되돌린다.
  - 결과를 알 수 없는 실패(타임아웃·오류)에서는 0단계 규칙대로 되돌리지 않는다.
  - 서비스 간 HTTP 자동 재시도는 계속 없다.
- **선착순 상품이 장바구니로 팔리는 것.** 이벤트 상품을 장바구니로 사면 오픈 시각과 이벤트 재고 규칙을 우회한다.

## 3. 제약
- 기존 스택 그대로: Java 25, Spring Boot 4.1.2, Spring Data JPA, Flyway, MySQL 8.4(서비스별 DB), Testcontainers, k6, Prometheus, Grafana.
- 새 컨테이너를 띄우지 않는다. 새 런타임 의존성도 되도록 넣지 않는다.
- 아키텍처 규칙 검사용 ArchUnit 은 테스트 의존성으로만 넣는다. **[설계자 판단]**
- `compose.yaml` 의 측정 기준 설정은 바꾸지 않는다. 대상은 컨테이너 한도, gateway 1280m·swap 없음, order-service 640m·Serial GC 다. 바꿔야 하면 사용자에게 먼저 묻는다. **[사용자 결정(앞 단계): 측정 기준을 바꾸는 설정은 묻고 바꾼다]**
- 저장소 규칙:
  - 커밋 메시지는 한국어, prefix 와 트레일러 없이 쓴다.
  - 커밋하는 파일에 로컬 절대 경로를 남기지 않는다.
  - push 하지 않는다.
  - 브랜치는 `feat/flash-sale-stage2`(1단계 브랜치에서 분기)이고 main 에 머지하지 않는다.

## 4. 구조: 서비스 안쪽의 헥사고날 [사용자 결정: DDD·헥사고날, 도메인 순수 자바 / 설계자 판단: 패키지 구성]

각 서비스의 루트 패키지(`com.flashsale.<service>`) 아래를 이렇게 나눈다.

| 패키지 | 들어가는 것 | 의존해도 되는 것 |
|---|---|---|
| `domain` | 애그리거트, 값 객체, 도메인 예외, 업무 규칙 | 자바 표준 라이브러리만 |
| `application` | 유스케이스를 수행하는 애플리케이션 서비스 | `domain`, `application.port.out`. Spring 의 `@Service`·`@Transactional` 은 허용 |
| `application.port.out` | 바깥으로 나가는 포트(저장소, 다른 서비스 호출, PG) 인터페이스 | `domain` |
| `adapter.in.web` | 컨트롤러, 요청·응답 DTO, 예외 → HTTP 응답 변환 | `application`, `domain` |
| `adapter.out.persistence` | JPA 엔티티, Spring Data 저장소, 포트 구현, 도메인 ↔ 엔티티 변환 | `application.port.out`, `domain` |
| `adapter.out.http` | 다른 서비스를 부르는 HTTP 클라이언트(포트 구현) | `application.port.out`, `domain` |
| `adapter.out.pg` (payment 만) | 가짜 PG 어댑터 | `application.port.out`, `domain` |
| `config` | 빈 조립, 설정 프로퍼티 | 전부 |

- **인바운드 포트 인터페이스는 두지 않는다.** 컨트롤러는 애플리케이션 서비스를 직접 부르고, 애플리케이션 서비스가 곧 유스케이스다. 단순함을 위한 선택이다. **[설계자 판단]**
- **애그리거트**: 회원(user), 상품(product; 선착순 이벤트는 product 의 별도 애그리거트로 유지), 재고(inventory), 장바구니·주문(order), 결제(payment). 장바구니와 주문은 같은 서비스 안의 서로 다른 애그리거트다. **[설계자 판단]**
- **규칙 검사**: 서비스마다 ArchUnit 테스트 하나로 위 의존 방향을 검사한다. `domain` 은 `org.springframework..`·`jakarta..` 금지, `application` 은 `adapter..` 금지. **[설계자 판단]**
- **게이트웨이는 구조를 바꾸지 않는다.** 라우팅과 JWT 검증만 하고 도메인이 없다. 새 경로의 라우트만 추가한다(§6). **[설계자 판단]**
- 기존 코드는 기능을 바꾸지 않고 이 구조로 옮긴다. 기존 테스트는 패키지만 따라 옮기고 계속 통과해야 한다.

### 재고 전략의 자리
- 1단계 `StockStrategy` 는 원래 인터페이스이고, 구현체가 모두 DB 기술(행 락, 버전 컬럼, 조건부 UPDATE, JPA 읽고-덮어쓰기)이다.
- 그래서 `StockStrategy` 를 `application.port.out` 의 포트로 두고, 구현체 4개는 `adapter.out.persistence` 로 옮긴다. 전략 선택 방식(`INVENTORY_STRATEGY`, `INVENTORY_OPTIMISTIC_MAX_RETRIES`)과 `GET /internal/strategy` 의 이름 규칙은 그대로다.
- 차감 결과(`DECREASED`, `OUT_OF_STOCK`, `CONFLICT`)와 통계(충돌·재시도 수)는 도메인 또는 애플리케이션 쪽 타입으로 둔다. 어느 쪽에 둘지는 빌더가 정한다.

## 5. 기능과 규칙

### 5.1 상품 (product-service)
- **카탈로그**
  - `GET /api/products?page=&size=`: 판매 상품의 id·이름·가격을 id 순으로 준다. 기본 size 20, 최대 100. 로그인은 필요 없다.
  - `GET /api/products/{productId}`: 같은 정보. 없거나 판매 상품이 아니면 404.
- **재고는 카탈로그에 보여 주지 않는다.** 품절 표시가 필요하면 inventory 호출이 늘어나므로 이번 범위에서 뺀다. 품절은 주문할 때 알게 된다. **[설계자 판단]**
- **선착순 이벤트 상품은 카탈로그 상품이 아니다.** 지금은 이벤트를 만들 때마다 상품 행이 하나 생긴다. 이 상품들은 목록·상세에 나오지 않고, 장바구니에 담을 수 없다. 이벤트 주문(`POST /api/orders`)으로만 팔린다. 구분 방법(컬럼, 조회 조건 등)은 빌더가 정한다. **[설계자 판단]**
- **상품 등록**은 기존 이벤트 생성처럼 내부 API 로 한다.
  - `POST /internal/products` 에 `{name, price}` 를 보내면 id 가 온다.
  - 재고는 기존 `PUT /internal/inventory/{productId}` 로 정한다.
  - 관리자 인증은 없다. 내부 API 는 지금처럼 게이트웨이에 노출하지 않는다. **[설계자 판단]**
- **여러 상품 한 번에 조회(내부)**: order-service 가 장바구니를 보여 주거나 주문할 때 쓴다. 예: `GET /internal/products?ids=1,2,3`. 판매 상품이 아닌 id 는 결과에서 빠지거나 판매 불가로 표시된다. 형태는 빌더가 정한다.

### 5.2 장바구니 (order-service)
- 로그인한 사용자마다 장바구니가 하나 있다. 장바구니는 상품 id 와 수량만 갖는다. 가격은 저장하지 않는다. **[설계자 판단]**
- API (모두 로그인 필요):
  - `GET /api/cart`: 항목마다 상품 id·이름·현재 가격·수량·소계를 주고, 합계도 준다. 이름과 가격은 보여 줄 때 product-service 에서 가져온다. 그사이 판매 상품이 아니게 된 항목은 표시만 하고 합계에서 뺀다.
  - `PUT /api/cart/items/{productId}` 에 `{quantity}` 를 보낸다. 담기와 수량 바꾸기를 이 요청 하나로 한다. 수량을 그 값으로 정하는 방식이라 같은 요청을 두 번 보내도 결과가 같다. 수량은 1~99다. 판매 상품이 아니면 거절한다. **[설계자 판단]**
  - `DELETE /api/cart/items/{productId}`: 항목을 뺀다. 없는 항목이어도 성공으로 답한다.
  - `POST /api/cart/checkout`: 장바구니 전체를 주문 한 건으로 만든다(§5.3).
- 장바구니 규칙(같은 상품은 한 줄, 수량 범위)은 `Cart` 애그리거트가 지킨다.

### 5.3 주문 (order-service) [사용자 결정: 장바구니 전체 주문, 가격 복사, 일괄 차감, 실패 시 재고 복구·장바구니 유지 / 설계자 판단: 세부]
주문은 이제 항목 여러 개를 갖는다. 항목은 상품 id, 주문 순간의 상품 이름과 단가, 수량이다. 주문 금액은 항목 소계의 합이다. 선착순 이벤트 주문은 항목이 하나인 주문이고, 지금처럼 `eventId` 를 갖는다. 장바구니 주문은 `eventId` 가 없다.

**장바구니 주문 흐름** (`POST /api/cart/checkout`). 기존 이벤트 주문처럼 원격 호출을 DB 트랜잭션 안에서 하지 않는다.

1. 장바구니가 비어 있으면 주문을 만들지 않고 400 `CART_EMPTY` 로 답한다.
2. product-service 에서 담긴 상품들의 이름·가격을 가져온다.
   - 판매 상품이 아닌 항목이 있으면 주문을 만들지 않고 400 `PRODUCT_UNAVAILABLE` 로 답한다.
   - product 호출이 실패하면 기존 사전 실패(`PRODUCT_TIMEOUT`/`PRODUCT_ERROR`)처럼 답한다.
3. `PENDING` 주문을 만든다. 가격은 여기서 항목에 복사한다.
4. inventory-service 에 **여러 상품 일괄 차감**을 요청한다(§5.4).
   - `OUT_OF_STOCK` → 주문 `FAILED`(`SOLD_OUT`).
   - 타임아웃·오류 → 주문 `FAILED`(`INVENTORY_TIMEOUT`/`INVENTORY_ERROR`). 재고는 되돌리지 않는다(결과를 모름).
5. 합계 금액으로 payment-service 에 결제를 한 번 요청한다.
   - `DECLINED` → 일괄 복구를 요청하고, 주문 `FAILED`(`PAYMENT_DECLINED`).
   - 타임아웃·오류 → 주문 `FAILED`(`PAYMENT_TIMEOUT`/`PAYMENT_ERROR`). 재고는 되돌리지 않는다.
6. 승인되면 주문 `PAID`. 그다음 이 주문에 들어간 상품 줄을 장바구니에서 지운다. 주문 중에 사용자가 새로 담은 상품은 남는다.
7. 실패하면 장바구니는 그대로 둔다. 사용자는 다시 주문할 수 있다.

- 응답 상태 코드는 기존 이벤트 주문과 같은 규칙(`PAID` 201, `FAILED` 는 사유별 `FailReasonStatus`)을 쓴다.
- 복구 요청이 실패하면 기존처럼 로그만 남긴다. 복구 재시도는 4단계 주제다.
- **주문 상태 규칙**은 `Order` 애그리거트가 지킨다. `PENDING` 에서만 `PAID` 또는 `FAILED` 로 바뀐다. 금액은 항목에서 계산된다.
- **이벤트 주문**(`POST /api/orders`)은 흐름을 바꾸지 않는다. 단건 차감·단건 복구, 실패 사유, 사전 실패 집계, 통계 API 가 모두 같다. 저장 구조만 "항목 1개짜리 주문"으로 바뀐다.

**주문 내역** (로그인 필요):
- `GET /api/orders?page=&size=`: 내 주문을 최신순으로 준다. 기본 size 20, 최대 100. 주문마다 id, 상태, 실패 사유, 금액, 만든 시각, 항목 수, 대표 상품 이름을 준다.
- `GET /api/orders/{orderId}`: 상세. 위 정보에 항목 전체(상품 id·이름·단가·수량·소계)를 더한다. 남의 주문이거나 없으면 404.
- 이벤트 주문도 내 주문 내역에 함께 나온다.

**저장 구조**:
- Flyway 마이그레이션으로 주문 항목 테이블을 추가한다.
- `orders.event_id` 는 NULL 을 허용하게 바꾼다.
- 기존 `orders` 의 단일 상품 컬럼은 항목 테이블로 옮긴다.
- 통계 API 가 쓰는 `event_id`·`status` 조회는 그대로 빨라야 한다(인덱스 유지).
- 기존 행을 옮길지 버릴지는 빌더가 정한다. 측정 스크립트는 실행마다 주문을 모두 지운다.

### 5.4 재고 (inventory-service)
- 새 내부 API 두 개:
  - **일괄 차감**: `{items:[{productId, quantity}]}` 를 받는다. 전부 차감하거나 하나도 차감하지 않는다.
  - **일괄 복구**: 같은 형식으로 전부 되돌린다.
- **일괄 차감은 선택된 전략과 관계없이 트랜잭션 하나 안의 조건부 UPDATE 로 한다.** 데드락을 막기 위해 상품 id 순서로 처리한다. 하나라도 0행이 갱신되면 전부 롤백하고 `OUT_OF_STOCK` 을 돌려준다. 재고 행이 없는 상품도 `OUT_OF_STOCK` 이다. **[설계자 판단]**
  - 이유: 1단계 전략들은 단일 행 실험용이다. 낙관적 락은 시도마다 autocommit 문장을 쓰므로 여러 행을 한 트랜잭션으로 묶을 수 없다. 장바구니 주문은 실험 대상이 아니므로 정확하고 단순한 방법 하나로 고정한다.
  - 그래서 `INVENTORY_STRATEGY` 는 이벤트 주문의 단건 차감에만 적용된다. naive 로 돌려도 장바구니 주문은 초과 판매하지 않는다. 이 사실을 README 에 적는다.
- 기존 단건 API(차감·복구·설정·조회·통계·전략)는 그대로다.

### 5.5 결제 (payment-service) [사용자 결정: 가짜 PG, 무작위 실패, 나중에 실제 PG 구현체 교체 / 설계자 판단: 세부]
- `application.port.out.PaymentGateway`: 금액과 주문 정보를 받아 승인 또는 거절을 돌려주는 포트.
- `adapter.out.pg.FakePaymentGateway`: 지금 `PaymentSimulator` 의 동작(지연 + 흔들림, 실패율 확률로 거절)을 그대로 한다.
- 어떤 PG 를 쓸지는 설정값(예: `payment.gateway=fake`)으로 고른다. 이번 단계의 구현체는 fake 하나뿐이다. 실제 PG 는 나중에 같은 포트의 다른 어댑터로 추가한다.
- 결제 기록(`Payment` 애그리거트)은 지금처럼 승인·거절 모두 저장한다.
- `GET/PUT /internal/payments/config` 와 `DELETE /internal/payments` 는 그대로 둔다. 설정 API 는 가짜 PG 의 설정을 읽고 바꾼다.
- **실패율 기본값을 0% 에서 10% 로 바꾼다.** 평소 서비스를 띄우면 결제가 무작위로 실패한다. **[설계자 판단]**
- **선착순 측정은 실패율 0% 로 고정한다.** `scripts/run-test.sh` 가 실행 전에 결제 설정의 실패율만 0 으로 바꾼다(지연·흔들림은 그대로). 결과의 `meta.json` 에는 지금처럼 결제 설정이 남는다. 지금 판정 규칙에서 `PAYMENT_DECLINED` 는 방식의 특성이 아니므로, 실패율이 0 이 아니면 선착순 실행이 `INCONCLUSIVE` 가 되기 때문이다. **[설계자 판단]**

### 5.6 회원 (user-service)
- 기능 변경은 없다. 회원가입·로그인(JWT)·테스트 사용자 생성 API 를 §4 구조로 옮긴다.

## 6. 게이트웨이 라우트
- `/api/products/**`: 지금처럼 로그인 없이 product-service 로 보낸다.
- `/api/cart/**`: 새로 추가. 로그인(JWT) 검증 뒤 `X-User-Id` 를 붙여 order-service 로 보낸다. 기존 주문 라우트와 같은 필터(인증, 하류 타임아웃 504)를 쓴다.
- `/api/orders/**`: 그대로다. 주문 내역 조회도 같은 인증을 거친다.
- 라우팅 테스트에 새 경로를 추가한다.

## 7. 테스트
- **도메인**: 순수 자바 단위 테스트를 쓴다(Spring 없이). 대상은 장바구니 규칙, 주문 금액 계산과 상태 전이, 재고 차감 규칙 등이다.
- **어댑터·API**: 지금처럼 Testcontainers MySQL 로 통합 테스트를 쓴다.
  - 일괄 차감의 전부-아니면-전무를 확인한다. 한 상품이 모자라면 다른 상품도 그대로여야 한다.
  - 동시 일괄 차감에서 초과 판매가 없어야 한다.
  - 장바구니 주문의 각 실패 경로를 확인한다(품절, 결제 거절 시 재고 복구와 장바구니 유지, 결과를 모르는 실패 시 복구 없음). 하류 서비스는 기존 `StubHttpServer` 방식으로 흉내 낸다.
  - 이벤트 상품을 장바구니에 담을 수 없어야 한다.
  - 남의 주문 상세는 404 여야 한다.
- **아키텍처 규칙**: 서비스마다 ArchUnit 테스트(§4).
- **기존 테스트**: 모두 통과해야 한다. 특히 재고 전략 계약 테스트와 `NaiveStockStrategyTest.concurrentDecreasesLoseUpdates`, 판정 스크립트 테스트(`scripts/test-verdict.sh`).

## 8. 완료 기준
1. §5 의 API 가 게이트웨이를 통해 동작한다. 사용자 흐름을 처음부터 끝까지 도는 스크립트 `scripts/smoke-shop.sh` 가 통과한다. **[설계자 판단]**
   - 흐름: 상품과 재고를 직접 만들고 → 회원가입·로그인 → 목록 → 장바구니 담기 → 주문 → 주문 내역.
   - 결제 실패율을 100% 로 바꾼 경우도 확인한다. 주문 `FAILED`(`PAYMENT_DECLINED`), 재고 원래대로, 장바구니 유지.
   - 끝나면 실패율을 원래 값으로 되돌린다.
2. §7 의 테스트가 모두 통과한다.
3. **선착순 회귀 확인**: 1단계 5차와 같은 매트릭스를 돌린다(7개 구성, 워밍업 1회 + 측정 3회, 500명이 1초 동안, 재고 100).
   - 판정이 같아야 한다. 정확한 구성 18회 모두 `OK`, naive 3회 모두 `OVERSOLD`, `INCONCLUSIVE` 0.
   - 지연 수치는 게이트웨이 메모리 측정(`docs/results/stage2-gateway-memory.md`)과 참고로 비교한다. 이벤트 주문에 항목 저장이 하나 늘기 때문이다.
   - 결과 문서를 `docs/results/` 에 남기고, 결과 README 표에 추가한다.
4. README 를 갱신한다.
   - 새 API
   - 결제 실패율 기본값과 측정 때 0% 고정
   - 일괄 차감은 전략과 관계없이 조건부 UPDATE
   - 2단계가 이커머스 기본 기능으로 바뀐 것과 Redis 보류
