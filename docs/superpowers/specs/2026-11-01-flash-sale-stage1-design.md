# 선착순 한정 판매 MSA — 1단계 설계 (DB 수준 해결)

- 작성일: 2026-11-01
- 범위: 1단계 (비관적 락, 낙관적 락, 조건부 UPDATE 를 같은 시나리오로 측정·비교)
- 전제: 0단계 설계 `2026-10-29-flash-sale-msa-design.md` 와 그 구현(브랜치 `feat/flash-sale-stage0`). 여기 적지 않은 규칙은 0단계 그대로다.
- 표기: **[사용자 결정]** 은 사용자가 정한 것, **[설계자 판단]** 은 대화 중 설계자가 정하고 사용자가 이의 없이 넘어간 것 또는 문서 작성 중 정한 것.

## 1. 의도와 이유

0단계에서 naive 차감(락 없이 읽고 → 비교하고 → 덮어쓰기)이 lost update 를 일으켜 재고 100개에 423~720개가 팔리는 것을 확인했다. 1단계는 이 **같은 원인 하나**를 DB 수준에서 막는 세 가지 방법을 구현하고, 0단계와 같은 k6 시나리오로 돌려 비교한다. **[사용자 결정]**

1단계가 답할 질문: **정확해진 대신 얼마나 느려지나, 그리고 왜 느려지나.** **[사용자 결정]**

"끝났다"의 기준은 세 가지를 모두 갖추는 것이다. **[사용자 결정]**
1. **정답** — 세 방식 모두 초과 판매가 없음을 확인한다.
2. **비용** — 방식별 p95/p99/RPS 를 naive 와 한 표에서 비교한다.
3. **원인** — 느려진 이유를 **기록된 지표**(DB 행 락 대기, 커넥션 풀 대기, 낙관적 락 충돌·재시도, 타임아웃)로 설명할 수 있다. 그 결과로 "DB 한 행에 몰리는 구조 자체의 한계"를 숫자로 말할 수 있으면 2단계(Redis)로 넘어갈 근거가 된다.

세 방식은 같은 문제(lost update)의 다른 해법이므로 "한 번에 한 문제" 원칙과 충돌하지 않는다. **[사용자 결정]**

## 2. 목표 / 비목표 / 안티 목표

### 목표
- `StockStrategy` 구현체 3개 추가: `pessimistic`, `optimistic`, `conditional`. naive 는 그대로 남긴다. **[사용자 결정]**
- 낙관적 락은 **충돌 시 재시도 횟수 0~3** 을 설정으로 바꿔 가며 측정한다. 0회는 "재시도 없는 본연의 모습" 기준점이다. **[사용자 결정]**
- 덜 팔림(재고가 남거나, 차감됐는데 주문이 실패함)과 타임아웃은 실패가 아니라 **방식의 특성으로 기록**한다. **[사용자 결정]**
- 원인 설명에 필요한 지표(MySQL 행 락 대기, 낙관적 락 충돌·재시도, 계층별 타임아웃)를 수집하고, **실행마다 결과 파일에 수치로 남긴다.**
- 측정 매트릭스(§7)를 모두 돌려 결과표와 1단계 요약 문서를 남긴다.

### 비목표
- Redis, 대기열, Kafka (2·3단계).
- 결제 실패·타임아웃으로 인한 정합성 (4단계). 결제 실패율은 0% 그대로.
- 1인 1개 구매 제한 (5단계).
- 사용자 수를 바꿔 가며 한계를 찾는 실험. 기준 조건(5000명, 재고 100) 하나로만 비교한다. **[사용자 결정: 끝 기준 C 선택, D 제외]**
- 특정 방식을 빠르게 만드는 튜닝 (풀 크기, 타임아웃, 격리 수준, 인덱스 등).

### 안티 목표 (기술적으로 돌아가도 이렇게 되면 실패)
- **naive 가 조용히 안전해지는 것.** 공용 `Inventory` 엔티티에 `@Version` 을 붙이면 naive 까지 낙관적 락이 된다. 낙관적 락은 별도 쿼리로 구현하고, 기존 특성 테스트 `NaiveStockStrategyTest.concurrentDecreasesLoseUpdates` 는 계속 통과해야 한다.
- **방식마다 조건이 달라지는 것.** 0단계 고정 설정(타임아웃, 컨테이너 제한, Tomcat/Hikari 기본값, virtual threads off)과 MySQL 기본값(REPEATABLE READ, `innodb_lock_wait_timeout` 50s)을 방식에 따라 바꾸지 않는다. **[사용자 결정: 고정 설정 유지]**
- **초과 판매의 두 번째 원인이 생기는 것.** 결과를 알 수 없는 차감(타임아웃 등)은 0단계처럼 재고를 복구하지 않는다. 서비스 간 HTTP 자동 재시도도 계속 없다. 낙관적 락 재시도는 inventory-service 안에서 DB 차감만 다시 하는 것이고, HTTP 재시도가 아니다.
- **"방식의 특성"과 "실행이 잘못됨"이 섞이는 것.** 덜 팔림을 특성으로 인정하는 대신, 방식과 무관한 실패(미오픈, 인증 실패, 예상 밖 오류)가 섞인 실행은 반드시 `INCONCLUSIVE` 로 걸러야 한다.
- **원인을 라이브 대시보드로만 설명하는 것.** 원인 지표가 결과 파일에 수치로 남지 않으면 나중에 비교·설명할 수 없다.
- **콜드 실행과 웜 실행을 섞어 비교하는 것.**

## 3. 제약
- 0단계 제약 그대로: 로컬 Mac 한 대, Docker VM 약 7.7GB, 절대 수치보다 상대 비교.
- 새로 띄우는 컨테이너는 MySQL 지표 수집기 하나뿐이고 작아야 한다(메모리 64m 수준). **[설계자 판단]**
- 기존 스택(Java 25, Spring Boot 4.1, JPA, Flyway, Testcontainers, k6, Prometheus, Grafana)을 그대로 쓴다.

## 4. 세 가지 방식 [사용자 결정: 세 방식 모두, 구현 세부는 설계자 판단]

모두 inventory-service 의 `StockStrategy` 구현체이고 `INVENTORY_STRATEGY` 로 고른다. 재고 행은 행사 상품당 1개이므로, 모든 요청이 **같은 한 행**을 두고 경쟁한다.

| 전략 이름 | 차감 방법 | 실패 결과 |
|---|---|---|
| `pessimistic` | 한 트랜잭션에서 `SELECT ... FOR UPDATE` 로 행을 잠그고 읽은 뒤, 수량을 비교하고 차감 | `OUT_OF_STOCK` |
| `conditional` | `UPDATE inventory SET quantity = quantity - ? WHERE product_id = ? AND quantity >= ?` 한 문장. 영향받은 행이 1이면 성공, 0이면 품절(행이 없으면 NotFound) | `OUT_OF_STOCK` |
| `optimistic` | 락 없이 `quantity, version` 을 읽고, 수량이 모자라면 품절. 충분하면 `UPDATE ... SET quantity = ?, version = version + 1 WHERE product_id = ? AND version = ?`. 영향받은 행이 0이면 충돌 → 최대 N회 다시 읽고 시도 | `OUT_OF_STOCK`, 재시도를 다 써도 충돌이면 `CONFLICT` |

- **낙관적 락 재시도** **[사용자 결정: 0~3회 / 설계자 판단: 나머지]**
  - 횟수 N 은 환경변수(예: `INVENTORY_OPTIMISTIC_MAX_RETRIES`)로 정한다. 재빌드 없이 컨테이너 재생성만으로 바꿀 수 있어야 한다.
  - 충돌하면 **기다리지 않고 바로** 다시 시도한다. 대기 시간을 넣으면 비교 변수가 하나 더 생긴다.
  - 재시도마다 **새 트랜잭션**에서 다시 읽어야 한다. REPEATABLE READ 에서는 같은 트랜잭션 안의 재조회가 처음 스냅샷을 그대로 보여 주므로 재시도가 의미 없어진다. JPA 1차 캐시도 같은 함정이니 낙관적 락은 엔티티 갱신이 아니라 쿼리로 구현한다.
  - 한 요청의 모든 시도는 **커넥션 하나를 쥔 채** 진행한다. 시도마다 읽기·갱신을 autocommit 문장으로 실행해 매번 새로 읽되, 시도 사이에 커넥션을 풀에 돌려주지 않는다. 풀에 돌려줬다가 다시 빌리면 풀 대기가 숨은 대기(백오프)가 되어 "바로 재시도"가 아니게 된다. 대신 재시도가 커넥션을 오래 붙잡는 비용은 Hikari pending 으로 드러나고, 그 값은 측정된다. **[설계자 판단]**
  - 시도 중 수량이 모자라게 되면 그 시점에 `OUT_OF_STOCK` 이다(충돌이 아님).
- **스키마**: 낙관적 락용 `version` 컬럼을 Flyway 마이그레이션으로 추가한다(`NOT NULL DEFAULT 0`). 엔티티에는 매핑하지 않거나, 매핑하더라도 `@Version` 은 쓰지 않는다. 재고 설정(`PUT /internal/inventory/{id}`)이 version 을 건드리지 않아도 낙관적 락의 정확성에는 문제가 없다.
- **복구(increase)**: 각 전략은 자기 방식으로 안전하게 복구한다(예: 조건부는 `quantity = quantity + ?`). 결제 실패율이 0% 라 1단계 측정에서는 호출되지 않는다. **[설계자 판단]**
- **전략 이름 노출**: `GET /internal/strategy` 는 낙관적 락일 때 재시도 횟수를 포함한 이름(`optimistic-r0` ~ `optimistic-r3`)을 돌려준다. RUN_ID 와 결과표 strategy 열이 이 이름을 그대로 쓴다. **[설계자 판단]**
- **전략 전환**: 네 전략이 한 jar 에 모두 들어 있으므로, 처음 한 번 빌드한 뒤에는 환경변수만 바꿔 inventory-service 를 다시 띄우면 된다(README 의 "재빌드 필요" 안내를 갱신). **[설계자 판단]**

## 5. 판정과 실패 기록

### 원칙 [사용자 결정을 적용한 설계자 판단]
사용자는 "타임아웃이 나면 방식의 특성으로 기록하고 건수를 남긴다"고 정했다. 이를 **부하로 생긴 타임아웃은 어느 계층에서 났든 특성**으로 넓혀 적용한다. 같은 MySQL 을 모든 서비스가 나눠 쓰므로, 재고 행의 락 경합이 다른 호출까지 느리게 만들 수 있기 때문이다. 타임아웃이 아닌 오류는 계속 특성이 아니다.

### 실패 사유 (order-service) [설계자 판단]
현재 `INVENTORY_ERROR` 하나로 묶인 재고 호출 실패를 나누고, 충돌과 다른 계층의 타임아웃을 구분한다.

| 사유 | 뜻 | 방식의 특성인가 |
|---|---|---|
| `SOLD_OUT` | 재고 없음 | 예 |
| `STOCK_CONFLICT` | 낙관적 락이 재시도를 다 쓰고도 충돌 | 예 |
| `INVENTORY_TIMEOUT` | order → inventory 호출이 read/connect timeout. 차감 여부를 알 수 없음, 재고 복구 안 함 | 예 |
| `PAYMENT_TIMEOUT` | order → payment 호출 타임아웃 | 예 |
| `PRODUCT_TIMEOUT` | order → product 행사 조회 타임아웃. **주문 행을 만들기 전**에 실패 | 예 |
| `ORDER_DB_TIMEOUT` | order-service 자기 DB 의 커넥션 획득 타임아웃(Hikari `connectionTimeout`)으로 PENDING 주문을 만들지 못함. **주문 행을 만들기 전**에 실패 | 예 |
| `INVENTORY_ERROR` | 타임아웃이 아닌 재고 호출 오류(5xx, 응답 파싱 실패 등) | 아니오 |
| `PAYMENT_ERROR` | 타임아웃이 아닌 결제 호출 오류 | 아니오 |
| `PRODUCT_ERROR` | 타임아웃이 아닌 행사 조회 오류 | 아니오 |
| `PAYMENT_DECLINED` | 결제 거절. 실패율 0% 라 나오면 안 됨 | 아니오 |

- inventory 의 차감 응답에 `CONFLICT` 결과가 추가되므로, order-service 가 이를 알아야 한다. 모르는 값을 받으면 지금 구조에서는 `INVENTORY_ERROR` 가 되어 판정이 `INCONCLUSIVE` 로 빠진다.
- **주문 행이 없는 실패의 집계**: `PRODUCT_TIMEOUT`·`PRODUCT_ERROR`·`ORDER_DB_TIMEOUT` 은 DB 에 주문 행이 남지 않으므로, order-service 가 사유별 메모리 카운터로 세어 `GET /internal/orders/stats` 응답에 함께 싣는다(예: `preOrderFailedByReason`). `DELETE /internal/orders` 가 이 카운터도 초기화한다.
- **PENDING 이 남는 경우는 특성이 아니다**: 차감·결제 뒤 `markPaid`/`markFailed` 가 실패하면 주문이 PENDING 으로 남는다(0단계 규칙 R5). 결제가 승인됐는데 PAID 로 기록되지 못한 주문일 수 있으므로, PENDING 이 남으면 **초과 판매가 가려졌는지 판단할 수 없다.** 타임아웃 때문이라도 `INCONCLUSIVE` 로 둔다.
- 클라이언트 응답 상태: `STOCK_CONFLICT` 는 409, `*_TIMEOUT` 은 504 를 제안한다(빌더가 바꿔도 됨). k6 는 상태 코드와 응답 본문의 `reason` 으로 분류한다.

### 계층별 타임아웃 [사용자 결정: 타임아웃도 특성, 건수를 결과에 남김]
타임아웃은 아래 계층에서 날 수 있고, 각각 따로 센다.
- order → inventory / payment / product (10s), order-service 자기 DB 커넥션 획득(30s): 위 표의 `*_TIMEOUT` 사유로 센다.
- gateway → order (30s): k6 가 게이트웨이 타임아웃 응답(빌더가 실제 상태 코드를 확인)으로 센다. 이때 order-service 는 요청을 계속 처리하므로 **DB 에는 PAID 로 남을 수 있다.**
- k6 요청 (60s): k6 가 요청 타임아웃으로 센다. k6 의 status 0 에는 연결 오류도 섞이므로, k6 오류 코드로 **타임아웃만** 골라 특성으로 세고 나머지 연결 오류는 분류되지 않은 응답으로 둔다. 마찬가지로 DB 에는 결과가 남을 수 있다.

### 판정 (4가지) [사용자 결정: UNDERSOLD 추가 / 설계자 판단: 세부 조건]
판매 수량의 기준은 **DB 의 PAID 주문 수**다(0단계와 같음).

- `OVERSOLD` — `paid > saleQuantity`. 유일한 실패.
- `INCONCLUSIVE` — 실행 자체를 믿을 수 없음. 아래 중 하나라도 해당:
  - 대기 후에도 pending > 0, 또는 `paid + failed + 주문 생성 전 실패` 가 USERS 와 다름.
  - "방식의 특성이 아닌" 사유(위 표의 "아니오")가 1건 이상.
  - k6 응답 중 분류되지 않은 것(401, 400 미오픈, 연결 오류, 그 밖의 5xx 등)이 1건 이상.
  - k6 와 DB 의 paid 가 설명되지 않게 어긋남: `k6 paid ≤ DB paid ≤ k6 paid + (게이트웨이 타임아웃 + k6 타임아웃)` 을 벗어나면 해당.
- `UNDERSOLD` — 위 둘이 아니고 `paid < saleQuantity`. 덜 팔림은 "재고가 남았나"가 아니라 "판매가 재고보다 적은가"로 본다. 타임아웃이 나면 재고는 0인데 판매가 모자랄 수 있기 때문이다.
- `OK` — 위 셋이 아니고 `paid == saleQuantity`.

`INCONCLUSIVE` 가 나오면 원인을 찾는다. 측정 버그면 고쳐서 다시 잰다. 부하로 생긴 타임아웃인데 아직 분류되지 않은 것이면 위 원칙대로 사유를 추가하고 다시 잰다. **어느 경우에도 고정 설정을 바꾸는 튜닝은 해결책이 아니다.** **[설계자 판단]**

`verify.json`·`report.md` 에는 판정과 함께 덜 팔린 수량(`saleQuantity − paid`), 남은 재고, `stockMismatch`(차감량 − paid; 양수면 "차감됐는데 판매 안 됨", 음수면 lost update)를 그대로 남긴다.

## 6. 관측

### 새로 수집할 지표 [사용자 결정: 원인 지표 / 설계자 판단: 도구]
- **MySQL**: mysqld-exporter 를 Compose 에 추가하고 Prometheus 가 수집한다. 최소한 InnoDB 행 락 대기 횟수(`Innodb_row_lock_waits`), 누적 대기 시간(`Innodb_row_lock_time`), 현재 대기 수(`Innodb_row_lock_current_waits`). 수집용 MySQL 계정은 초기화 SQL 에 추가한다.
- **낙관적 락**: inventory-service 의 Micrometer 카운터로 충돌 횟수, 재시도 횟수, 최종 `CONFLICT` 횟수.
- 기존 지표(서비스별 요청률·p95, Tomcat busy, Hikari active/pending, CPU, heap, 에러율, k6)는 그대로.

### 대시보드
`flash-sale` 대시보드에 패널을 추가한다: MySQL 행 락 대기(비율, 대기 시간, 현재 대기 수), 낙관적 락 충돌·재시도 비율, 타임아웃 응답 비율. **[설계자 판단]**

### 실행마다 남길 원인 지표 [설계자 판단]
`run-test.sh` 가 k6 실행 구간의 값을 Prometheus 에서 조회해 `report.md` 에 "원인 지표" 절로 남긴다. 최소한:
- MySQL 행 락 대기 횟수·누적 대기 시간의 구간 증가량, 현재 대기 수의 최댓값.
- 서비스별 Hikari pending 최댓값, Tomcat busy threads 최댓값.
- 낙관적 락 충돌·재시도·최종 CONFLICT 의 구간 증가량.
- 계층별 타임아웃 건수(§5).
- inventory 차감 엔드포인트의 **서버 측** p95, 그리고 payment 호출 수. naive 는 초과 판매 탓에 결제 호출이 몇 배 많아서, 끝단(k6) p95 만으로는 정확한 방식이 오히려 빨라 보일 수 있다. 이 값은 나중에 다시 계산할 수 없으므로 실행마다 남긴다.

Prometheus 스크레이프 간격(지금 5s)은 측정 정밀도를 위해 빌더가 줄여도 된다. 관측 설정이며 고정 설정이 아니다. 바꾸면 고정 설정 절에 함께 기록한다.

`report.md` 의 "고정 설정" 절에 MySQL 격리 수준과 `innodb_lock_wait_timeout`, Hikari `connectionTimeout`(기본 30s)을 추가한다.

### 결과표 [사용자 결정: 남은 재고·충돌·타임아웃·재시도 열]
`docs/results/README.md` 표에 열을 추가한다: 남은 재고, 덜 팔림, 충돌(최종 CONFLICT 수), 타임아웃(계층 합계), 재시도 총횟수. 기존 naive 행은 원본 기록(`verify.json`, `order-stats.json`)으로 다시 계산할 수 있는 값만 채우고 나머지는 `-` 로 둔다. **[설계자 판단]**

## 7. 측정 절차 [사용자 결정: 방식별 3회, 워밍업 / 설계자 판단: naive 재측정, 워밍업 방식]

| 구성 | 측정 |
|---|---|
| `naive` (1단계 환경에서 재측정) | 3회 |
| `pessimistic` | 3회 |
| `conditional` | 3회 |
| `optimistic-r0` / `r1` / `r2` / `r3` | 구성마다 3회, 총 12회 |

- 구성을 바꿀 때마다 inventory-service 를 다시 띄우므로 **구성마다 워밍업 1회**를 먼저 돌린다. 워밍업도 기록은 남기되 결과표에서 워밍업임을 표시해 비교에서 뺀다.
- **naive 를 다시 재는 이유**: 1단계는 order-service 의 실패 분류와 지표 수집기가 바뀌어 환경이 0단계와 조금 다르다. 같은 환경의 naive 를 기준선으로 써야 공정하다. 0단계 기준선은 참고로 그대로 둔다.
- 모든 실행은 기준 조건(USERS 5000, SALE_QUANTITY 100)이다. **워밍업도 같은 규모로** 돌린다. 2026-11-01 사용자 실행(0단계 코드, 기록은 삭제함)에서 200명 워밍업 직후의 5000명 실행 p95 가 11.65s 로, 0단계 웜 실행(8.8s / 7.6s)보다 느렸다. 작은 워밍업으로는 충분히 데워지지 않는다는 근거다. **[설계자 판단]**
- 매트릭스 전체를 한 번에 돌리는 스크립트를 둘지는 빌더 판단이다.

## 8. 1단계 완료 기준
- 네 전략이 테스트로 검증돼 있다. 최소한: 동시 차감 테스트에서 `pessimistic`·`conditional`·`optimistic` 은 성공 수가 재고를 넘지 않고 `성공 수 + 남은 재고 = 초기 재고`, naive 특성 테스트는 그대로 lost update 를 보인다.
- §7 매트릭스 21회(워밍업 제외)를 모두 돌렸고, **세 방식 모두 `OVERSOLD` 0회, `INCONCLUSIVE` 0회**다. `OK`·`UNDERSOLD` 는 결과로 기록한다. `INCONCLUSIVE` 가 나오면 원인을 고쳐 다시 잰다.
- 1단계 naive 재측정 3회는 모두 `OVERSOLD` 다.
- 결과표에 모든 실행이 새 열과 함께 기록돼 있고, 각 `report.md` 에 원인 지표 절이 있다.
- Grafana 에서 MySQL 행 락 대기와 낙관적 락 충돌·재시도를 볼 수 있다.
- **1단계 요약 문서**(`docs/results/stage1-summary.md`)가 있다: 구성별 3회의 중앙값으로 정답·비용을 한 표에 놓고, 원인 지표로 "왜 그만큼 느려졌나 / 왜 덜 팔렸나"를 설명하고, 2단계로 넘어갈 근거를 적는다. **[설계자 판단]**

## 11. 측정 중 바뀐 것 (2026-11-02~03)
- **측정 간 대기**: 연속 실행에서 직전 실행의 소켓이 호스트에 TIME_WAIT 로 남아 연결 단계 실패가 나서, k6 시작 전 TIME_WAIT < 500 을 기다린다(1차 측정 무효, `docs/results/stage1-attempt1/`).
- **INCONCLUSIVE 처리**: 2차 측정에서는 연결 단계 실패로 INCONCLUSIVE 가 된 실행을 빼고 다시 재 대신했다. 사용자는 이 처리 대신 깨끗한 환경 재측정을 택했다(`stage1-attempt2/`).
- **k6 실행 위치** [사용자 결정]: 다른 컨테이너를 멈추고 Docker Desktop 을 재시작한 3차 측정에서도 같은 실패가 나왔다(`stage1-attempt3/`). 원인은 호스트 `localhost:8080` 을 받는 Docker Desktop 중계 계층이다. 그래서 4차부터는 k6 를 Docker 네트워크 안 컨테이너(`grafana/k6:2.2.0`, cpus 4 / memory 2g)로 돌려 `gateway:8080` 에 직접 연결한다. k6 가 측정 대상과 같은 VM 자원을 나눠 쓰므로 그 한도를 결과에 기록한다. naive 도 같은 방식으로 다시 재므로 1단계 안 비교는 유지되지만, 0단계 기준선(호스트 k6)과의 절대 비교는 참고로만 쓴다.
