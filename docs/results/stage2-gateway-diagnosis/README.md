# 2단계 게이트웨이 60초 타임아웃 원인 조사

2단계 매트릭스(`../stage2-summary.md` §4)에서 k6 요청이 60초 타임아웃에 걸린 실행이 4번 나왔다. 그중 3번이 `INCONCLUSIVE`(`order-total`)다.
타임아웃 난 요청은 주문이 생기지 않았고, 게이트웨이 504 도 없었다. 2026-11-03 19시대에 진단 실행 32회로 원인을 확인했다.

## 결론

- **원인은 게이트웨이의 연결 대기열(listen backlog) 100칸이다.** 연결 5000개가 같은 순간에 몰리면 이 대기열이 넘친다.
  - 넘치면 커널이 연결 요청(SYN)·연결 완료(ACK)·요청 데이터를 버린다(`ListenOverflows`).
  - 클라이언트(Linux TCP)는 버려진 패킷을 0.2초부터 대기 시간을 두 배씩 늘려 다시 보낸다.
  - 연결이 모두 같은 순간에 시작했으므로, 다시 보내는 시점도 6.2·12.6·25.4·51.0초에 한꺼번에 몰린다. 그때마다 대기열이 또 넘쳐, 한 번에 약 100~200건만 들어간다.
  - 51초에도 못 들어간 요청은 다음 재전송이 약 102초 뒤다. 그래서 k6 의 60초 타임아웃에 걸린다.
  - 이 요청들은 게이트웨이 애플리케이션에 닿지 않는다. 그래서 504 도 주문도 없다.
- **게이트웨이 swap 과 GC 정지는 꼭 있어야 하는 원인이 아니다.**
  - swap 을 없애도(아래 b) 8회 중 2회가 53초까지 늘어졌다.
  - 반대로 swap 과 1.4~1.6초 Full GC 를 그대로 두고 대기열만 4096칸으로 늘리자(c), 8회 모두 넘침이 거의 0이었고 늘어진 실행도 없었다.
- **실행마다 결과가 다른 이유:** 첫 몰림에서 대기열이 얼마나 넘치느냐에 달렸다. 넘침은 실행마다 0~16,850건으로 흔들렸고, 1.5만 건을 넘은 실행만 50초 이상 늘어졌다.
  - 넘침 양은 그 순간 게이트웨이가 연결을 얼마나 빨리 받아 가느냐에 달린 것으로 보인다. 게이트웨이는 CPU 2개를 Tomcat worker 200개·JIT·GC 와 나눠 쓴다.
  - 2단계(28회 중 5회)가 1단계 4차(28회 중 1회)보다 많았던 이유는 정하지 못했다. 같은 설정에서도 8회 중 0~2회로 흔들린다.
- **별개 문제: 게이트웨이가 swap 을 쓰고 있다.**
  - 640m 한도인데 JVM 이 약 800 MiB 를 쓴다. 그래서 약 300 MiB 가 swap 에 있다.
  - 그 결과 young GC 가 0.4~1.2초, Full GC 가 0.6~1.8초씩 멈춘다. swap 이 없으면 첫 실행을 빼고 둘 다 0.1초 안팎이다.
  - 이 정지는 지연을 키운다. 다만 타임아웃의 원인은 아니다.

## 게이트웨이가 연결을 받는 구조

게이트웨이는 Spring Cloud Gateway **Server WebMVC**(`spring-cloud-starter-gateway-server-webmvc`)다. Tomcat 위에서 돈다.
연결을 받는 단계는 세 층이고, 숫자 셋은 서로 다른 층의 한도다.

| 층 | 한도 (Spring Boot 기본값) | 하는 일 | 넘치면 |
|---|---|---|---|
| 커널 listen 대기열 | `accept-count` 100 | TCP 연결 맺기가 끝난 연결이 Tomcat 의 Acceptor 스레드(1개)가 `accept()` 할 때까지 기다린다 | **커널이 SYN/ACK 를 버린다** (`ListenOverflows`) |
| Tomcat 연결 (NIO Poller) | `max-connections` 8192 | 받아들인 연결을 selector 로 지켜본다. 데이터가 올 때까지 스레드를 쓰지 않는다(이벤트 기반) | Acceptor 가 받기를 멈춘다(그러면 위 대기열이 찬다) |
| 작업 스레드 | `threads.max` 200 | 요청 하나를 읽고 order-service 응답을 받아 돌려줄 때까지 스레드 하나가 맡는다(요청당 스레드, 블로킹) | 요청이 스레드를 기다리며 줄을 선다. 버려지지 않는다 |

Prometheus 의 `tomcat_connections_config_max_connections` 는 8192, `tomcat_threads_config_max_threads` 는 200 이다. `ss -ltn` 으로 본 대기열은 100 이다.
정상 실행 20261103-172116-naive 의 k6 시작 +5초 표본에서, 게이트웨이는 연결 5,004개를 한꺼번에 쥐고 있었다. 이때 일하던 스레드는 188개였다.
늘어진 실행 171909 는 연결 수가 +2초 2,143개에서 +10초 3,985개로 천천히 늘었다. 나머지 약 1,000개는 그동안 TCP 재전송 속에 있었다.
(+2~+4초 표본이 빠진 것은 게이트웨이가 바빠서 1초 스크레이프가 실패했기 때문이다.)

그래서 버려지는 곳은 맨 앞의 커널 대기열 하나뿐이다. 5,000개는 8192 보다 적어서, Tomcat 은 모두 받아들일 수 있다.
연결 5,000개가 0.25초 안팎에 몰리는데, Acceptor 스레드 하나가 CPU 2개를 작업 스레드·JIT·GC 와 나눠 쓰며 연결을 꺼낸다. 이 속도가 도착 속도를 따라가지 못하면 100칸이 넘친다.

## 근거

### 1. 늘어진 시간은 연결 단계가 아니라 응답 대기 단계에 있다

k6 요약(`runs/<RUN_ID>/k6-summary.json`)의 단계별 최댓값:

| 실행 | connecting 최대 | waiting 최대 | 응답 최대 |
|---|---|---|---|
| 20261103-171909-naive (2단계, 타임아웃 418) | 3.6s | 58.8s | 58.8s |
| 20261103-172314-conditional (2단계, 타임아웃 17) | 3.6s | 58.8s | 58.8s |
| 20261103-172949-optimistic-r2 (2단계, 타임아웃 26) | 2.1s | 58.8s | 58.8s |
| 20261103-155008-conditional (1단계 4차, 늘어진 유일한 실행) | 2.1s | 52.5s | 52.5s |
| 20261103-172116-naive (2단계, 정상) | 1.1s | 4.5s | 4.5s |

연결 단계 최대 1.1~3.6초는 연결 요청(SYN)을 다시 보낸 흔적이다. 정상 실행에도 있다.
수십 초 늘어진 부분은 모두 waiting(요청을 보낸 뒤 첫 바이트까지)에 있다.
대기열이 꽉 찬 상태에서 연결 완료(ACK)가 버려져도, 클라이언트는 연결된 줄 알고 요청을 보낸다. 그 요청을 다시 보내는 시간이 waiting 에 잡힌다.

### 2. 게이트웨이 대기열은 100칸이고 계속 넘친다

- `ss -ltn` 으로 본 게이트웨이 `*:8080` LISTEN 의 Send-Q(대기열 한도)는 100 이다. Tomcat `server.tomcat.accept-count` 기본값이다.
  컨테이너의 `net.core.somaxconn` 은 4096 이라 상한이 되지 않는다. syncookies 는 켜져 있다.
- 게이트웨이 컨테이너 안 `/proc/net/netstat` 누적값(2단계 매트릭스 끝): `ListenOverflows` 204,901, `TCPReqQFullDoCookies` 69,044, `SyncookiesRecv` 189,732.
- order-service 의 `*:8084` 도 100칸이지만 `ListenOverflows` 는 0 이다. 게이트웨이가 order-service 에 연결 풀로 붙어서, 연결이 한꺼번에 몰리지 않는다.
- 진단 실행의 0.25초 표본(`tools/timeline.sh`)에서 넘침은 k6 시작 직후(연결 5000개 몰림)와 약 1초 뒤(SYN 재전송)에 몰린다.

### 3. 응답 대기 시간이 재전송 시점에 계단처럼 몰린다

`waiting-histogram.txt` 에서 50초 이상 늘어진 3회와 정상 1회만 옮긴다(구간 시작 초: 건수).

| 실행 | 0~3.5초 | 6.5초 | 13초 | 26초 | 52~53초 | 58초(타임아웃) |
|---|---|---|---|---|---|---|
| a8 | 4,306 | 184 | 150 | 193 | 110 | 57 |
| b1 | 4,282 | 308 | 139 | 136 | 135 | – |
| b2 | 4,482 | 204 | 159 | 119 | 36 | – |
| b3 (정상) | 5,000 | – | – | – | – | – |

4~6초, 7~12초, 14~25초, 27~51초 구간은 비어 있다.
재전송은 0.2초에서 시작해 두 배씩 늘므로 누적 시점이 6.2·12.6·25.4·51.0초다. 계단이 정확히 그 자리에 있다.
계단 하나에 들어간 요청은 약 100~200건으로, 대기열 100칸에 그 사이 게이트웨이가 받아 간 만큼을 더한 수다.
a8 은 51초에도 57건이 남았다. 이 57건은 다음 시점(약 102초)을 기다리다 k6 타임아웃에 걸렸다. 주문 수도 4,943건으로 정확히 57건이 모자랐다.

2단계 매트릭스에서도 같은 모양이었다. k6 원격 기록(5초마다 보냄)으로 본 응답 완료 시각(k6 시작 기준)은 이렇다.
- 171909: +6, +10, +17, +29, +55~56초, 그리고 +60초 타임아웃 418건
- 172314: +6, +10, +16~17, +30, +56초, 그리고 +62초 타임아웃 17건

### 4. 게이트웨이는 swap 중이다 (별개 문제)

2단계 매트릭스 뒤 각 컨테이너의 cgroup 값:

| 컨테이너 | 메모리 한도 | swap 사용 | swap 에서 다시 읽은 anon page | 메모리 한도 도달 | major fault |
|---|---|---|---|---|---|
| gateway | 640 MiB | 247 MiB | 1,484,652 | 54,617 | 924,722 |
| order-service | 1 GiB | 0 | 0 | 0 | 6 |
| payment-service | 640 MiB | 0 | 0 | 0 | 0 |
| product-service | 640 MiB | 0 | 0 | 0 | 0 |

- Docker VM 의 swap 파일(1 GiB)에서 쓰인 254 MiB 는 거의 다 게이트웨이 몫이다.
  Docker 는 `--memory` 만 주면 같은 크기의 swap 을 더 허용한다(`memory.swap.max` = 640 MiB).
- JVM 이 보고하는 메모리는 heap 433 MiB 와 non-heap 92 MiB 다. 그런데 프로세스는 RSS 628 MiB 에 swap 170 MiB 로, 약 800 MiB 를 쓴다.
  heap 이 컨테이너의 70%(448 MiB)라, 나머지 192 MiB 로는 스레드 스택·JIT·GC·네이티브 메모리를 다 담지 못한다.
- 새로 만든 게이트웨이도 첫 실행부터 swap 이 300 MiB 를 넘었다(a1).

## 실험: 한 번에 하나씩 바꿔 본 게이트웨이

모든 진단 실행은 `tools/diag-run.sh` 로 돌렸다. 단계는 `scripts/run-test.sh` 와 같다.
- 데이터 초기화, 재고 100, 토큰 5000개, 같은 k6 스크립트와 k6 컨테이너 한도(cpus 4 / 2g)
- inventory 전략은 naive
- 결과는 `docs/results` 표에 넣지 않았다

r 을 뺀 각 군은 게이트웨이를 새로 만든 뒤 smoke 1회를 하고 8회 돌렸다. 바꾼 설정은 `tools/*-override.yaml` 이다(`docker compose -f compose.yaml -f <override> up -d gateway`).
실험 뒤에는 `compose.yaml` 그대로 게이트웨이를 다시 만들었다. 대기열 100, 640M, Serial GC, `JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=70` 인 것을 확인했다.

| 군 | 게이트웨이 설정 | 대기열 넘침 | swap 최대 | young GC 최대 | Full GC 최대 | 응답 최대 | 50초 넘게 늘어진 실행 | 주문 누락 |
|---|---|---|---|---|---|---|---|---|
| r | 2단계 매트릭스 뒤 그대로 (640m, heap 448 MiB, 대기열 100) | 0~5,963 | 285~320 MiB | 644~1,248ms | 806~1,120ms | 4.0~7.3s | 0/8 | 0 |
| a | 원래 설정, 새 컨테이너 | 3,313~16,850 | 302~346 MiB | 358~924ms | 1,630~1,822ms | 3.3~58.8s | 1/8 (a8) | 57 (a8) |
| b | 메모리 1g + `-Xmx448m` (heap·GC 같음, swap 압박만 없앰) | 219~16,588 | 0 | 69~620ms (첫 실행 620, 나머지 69~130) | 86~101ms | 2.9~53.4s | 2/8 (b1, b2) | 0 |
| c | 원래 설정 + `SERVER_TOMCAT_ACCEPTCOUNT=4096` (대기열만 늘림) | 0~89 | 140~336 MiB | 527~830ms | 1,413~1,566ms | 4.4~6.4s | 0/8 | 0 |

실행별 값은 `runs-summary.txt` 에 있다. GC 열은 Prometheus 1초 표본이다. 원본 표본은 `runs/<이름>/` 에 있다.
- `gw.txt`: 게이트웨이 카운터 0.25초 표본
- `k6-summary.json`, `order-stats.json`, `times.txt`
- `req.csv.gz`: k6 요청별 값. a8·b1·b2·c8 만 남겼다

b 에서 swap 을 없애자 GC 정지는 10분의 1로 줄었다. 그래도 대기열 넘침과 50초 늘어짐은 남았다.
c 에서는 swap 과 긴 GC 가 그대로인데 넘침과 늘어짐이 사라졌다. 그래서 타임아웃을 결정하는 것은 대기열 크기다.

c 에서는 요청이 버려지지 않고 모두 바로 들어와, 응답 대기가 0~6초에 고르게 퍼졌다.
p99 는 4.4~6.3초로, 같은 swap 상태인 a 의 늘어지지 않은 실행(3.1~6.7초)과 겹친다.
지금까지 요청 일부는 TCP 재전송 속에서 줄을 서고 있었다. 대기열을 늘리면 그 줄이 게이트웨이와 order-service 안으로 옮겨 온다.
그래서 대기열 크기를 바꾸면 끝단 지연의 분포가 달라질 수 있다. 바꾼다면 0~2단계와 비교할 기준을 새로 잡아야 한다.

## CPU 를 늘리면 나아지나

게이트웨이의 CPU 한도만 2 → 4 → 8 로 바꿨다. 메모리 640m, heap 448 MiB, Serial GC, 대기열 100 은 그대로 뒀다.
override 는 `tools/gw-cpu{4,8}-override.yaml` 이다. 대조군 k 는 원래 설정(cpus 2)으로 같은 시간대에 다시 돌렸다.
이번에는 표본기에 게이트웨이 CPU 사용량(cgroup `cpu.stat`)을 더했다. 군마다 새 컨테이너로 8회씩 돌렸다.

| 군 | 게이트웨이 CPU | 대기열 넘침 | CPU 사용 최대 (0.25초 표본) | 응답 최대 | 13초 넘게 늘어짐 | 50초 넘게 늘어짐 | 주문 누락 |
|---|---|---|---|---|---|---|---|
| k | 2 | 1,456~16,845 | 123~238% | 3.4~13.6s | 3/8 | 0/8 | 0 |
| d | 4 | 772~19,036 | 122~367% | 3.2~58.8s | 3/8 | 1/8 (d1) | 30 (d1) |
| e | 8 | 784~13,440 | 133~499% | 3.4~53.0s | 2/8 | 1/8 (e6) | 0 |

**CPU 를 늘려도 넘침과 늘어짐은 줄지 않았다.** 넘침 범위가 세 군 모두 비슷하고, 50초 넘게 늘어진 실행은 오히려 CPU 4개·8개 쪽에서 나왔다.
군마다 8회라 이 횟수 차이 자체는 의미를 두기 어렵다. 다만 "CPU 를 늘리면 줄어든다"는 모양은 보이지 않는다.

연결이 몰리는 순간(k6 시작 약 1.8초 뒤)의 표본을 보면, 넘칠 때 게이트웨이의 사정이 실행마다 다르다.
- **e6 (CPU 8개, 53초까지 늘어짐):** 0.25초마다 2,221 / 2,217 / 1,108건이 넘쳤다. 그런데 이때 CPU 사용은 34~45%에 그쳤다(한도 800%). 대신 major fault 가 0.25초마다 약 5천 건이었다. CPU 가 남는데도 게이트웨이가 swap 에서 메모리를 다시 읽느라 멈춰 있었다.
- **d1 (CPU 4개, 새 컨테이너의 첫 실행, 58.8초까지 늘어짐):** swap 이 아직 없을 때다. CPU 사용이 337~343% 로 한도(400%)에 거의 닿았다. 첫 실행은 young GC 가 93번 나고 JIT 도 바쁘다. 그래서 CPU 를 다 쓴 상태에서 7,017 / 3,713건이 넘쳤다.
- **k1 (CPU 2개, 첫 실행):** CPU 사용이 197~238% 로 한도에 닿은 상태에서 넘쳤다.
- **e7 (CPU 8개, 정상):** 넘침 214건, CPU 사용 103%.

정리하면 이렇다.
- Tomcat 은 연결을 꺼내 가는 Acceptor 스레드가 하나뿐이다. CPU 개수를 늘려도 그 스레드 하나의 속도는 그대로다.
- swap 때문에 멈추는 경우(e6)에는 CPU 가 남아 있어도 소용이 없다.
- 멈춤이 없는 실행(b 군의 swap 없는 정상 실행)에서도 수백~수천 건씩 넘쳤다.
- 연결 5,000개가 0.25초 표본 하나 안에 몰려 도착한다. 그래서 100칸 대기열을 그 속도로 비우기는 받아 가는 쪽을 아무리 빠르게 해도 어렵다. 끝까지 넘침을 없앤 것은 대기열을 넓힌 c 군뿐이다.

## heap 1GiB · swap 금지에서 CPU 를 늘리면

설정은 다음과 같다.
- 게이트웨이 heap 1GiB(`-Xmx1g`), GC 는 원래와 같은 Serial(`-XX:+UseSerialGC`)
- 컨테이너 메모리 2g, `memswap_limit` 2g(swap 금지)
- 대기열은 원래대로 100. CPU 만 2 → 4 → 8 로 바꿨다(`tools/gw-heap1g-noswap-cpu{2,4,8}-override.yaml`)

메모리를 2g 로 둔 이유: heap 1GiB 에 heap 밖 메모리를 더하면 1g 를 넘는다. 측정 뒤 RSS 가 1.48~1.52 GB 였다.
GC 를 Serial 로 못박은 이유: 컨테이너가 약 1.8GB 이상이면 JVM 이 스스로 G1 을 고르기 때문이다.
세 군 모두 OOM 종료·재시작은 없었고, swap 사용과 major fault 는 사실상 0 이었다.

| 군 | CPU | 대기열 넘침 | CPU 사용 최대 | young GC 최대 (1~3회 / 4~8회) | 응답 최대 | p95 | 13초 넘게 | 50초 넘게 | 잃은 요청 |
|---|---|---|---|---|---|---|---|---|---|
| f | 2 | 21~17,612 | 108~241% | 392~741 / 57~119ms | 2.9~58.9s | 2.8~53.2s | 2/8 (f1, f2) | 1/8 (f1) | 203 (f1) |
| g | 4 | 84~10,812 | 111~401% | 379~515 / 38~101ms | 3.0~6.6s | 2.8~3.8s | 0/8 | 0/8 | 0 |
| h | 8 | 0~12,724 | 116~435% | 331~512 / 63~99ms | 2.9~3.7s | 2.8~3.6s | 0/8 | 0/8 | 0 |

**새로 띄운 직후 1~3회와, 그 뒤 4~8회는 다르게 움직였다.**
- **1~3회:** 실행마다 young GC 가 54~90번 났다. heap 이 작은 초기 크기에서 커지는 동안이다. JIT 도 아직 바쁘다.
  - CPU 2개(f1, f2)는 이때 CPU 를 다 쓰면서 늘어졌다. f1 은 51초 차례에도 못 들어간 203건을 잃었다.
  - CPU 4·8개(g1~3, h1~3)는 같은 시기에 넘침이 5천~1만2천 건이었지만, 늘어짐은 6.6초 이하였다.
- **4~8회(데워진 뒤):** 세 군 모두 응답 최대 2.9~4.0초, 13초 넘게 늘어진 실행 0/15, 잃은 요청 0 이었다. young GC 는 실행당 2~4번, 최대 119ms 다.
  - 넘침은 여전히 0~4,511건씩 있었다. 다만 재전송 첫 몇 차례 안에 모두 들어갔다.

데워진 뒤(4~8회)만 앞의 군들과 견주면 이렇다.

| 조건 | 군 | 4~8회 중 13초 넘게 늘어진 실행 |
|---|---|---|
| 640m, swap 있음, heap 448 MiB | a, k, d, e (CPU 2·2·4·8) | 20회 중 4회 (a8 58.8s, k8 13.3s, d4 26.4s, e6 53.0s) |
| 1g, swap 안 씀, heap 448 MiB, CPU 2 | b | 5회 중 1회 (b8 13.3s) |
| 2g, swap 금지, heap 1GiB | f, g, h (CPU 2·4·8) | 15회 중 0회 |

정리하면 이렇다.
- swap 이 있을 때는 CPU 를 늘려도 소용없었다(앞 절). 반면 swap 이 없고 heap 이 넉넉하면, 데워진 뒤에는 CPU 2개로도 늘어짐이 없었다.
- CPU 가 차이를 낸 것은 새로 띄운 직후의 몇 회뿐이다. 이때는 CPU 2개만 늘어졌다.
- 하지만 커널 대기열 넘침 자체는 모든 군에서 거의 매번 있었다(0~17,612). 이 설정들은 버려진 연결이 재전송으로 빨리 들어오게 해 줄 뿐, 버리는 일 자체를 없애지는 않는다. 넘침을 거의 없앤 것은 대기열을 4096칸으로 늘린 c 군뿐이다(0~89).
- 군마다 8회라 "0/8" 은 일어나지 않는다는 보장이 아니다.

## 처리가 가벼운데 왜 넘치나

결제까지 가는 요청은 100건뿐이고, 나머지 4,900건은 매진 응답을 받는다. 그래도 타임아웃이 나는 이유를 정리한다.

**1. 타임아웃이 난 곳은 DB 커넥션이 아니라 TCP 연결이다.**
- 1단계 4차와 2단계의 측정 56회에서 order-service 의 DB 커넥션 타임아웃(Hikari 30초, `timeouts.orderDb`)은 0건이다.
- 60초 타임아웃은 사용자 → 게이트웨이 TCP 연결을 받아들이는 단계에서 났다.
- 이 단계에서는 게이트웨이가 아직 HTTP 요청을 읽지 않았다. 그래서 이 요청이 결제할 요청인지 매진될 요청인지 알 수 없다. 처리가 가볍다는 사실이 여기서는 도움이 되지 않는다.

**2. 넘침은 처리가 시작되기 전, 연결이 몰리는 순간에 난다.**
- 진단 실행의 0.25초 표본에서, 넘침은 k6 가 시작하자마자 한 표본 안에 수천 건씩 나왔다(a8 4,072건, a6 2,986건, r1 1,272건).
- 연결 5,000개가 0.25초 안팎에 거의 다 도착한다. 대기열은 100칸이라, 게이트웨이가 그만큼 빨리 받아 가지 못하면 넘친다.
- 처리 능력이 충분하다는 근거도 있다. 대기열만 4096칸으로 늘린 c 군에서는 5,000건이 모두 들어와 4.4~6.4초 안에 끝났다. 문이 좁았던 것이지 안쪽이 막힌 것이 아니다.

**3. 다만 매진 요청도 공짜는 아니다. 부하 때 지연(p95 3.2~3.8초)은 이것으로 설명된다.**
- 매진 요청도 order-service 에서 DB 커넥션을 두 번 쓴다. 주문 PENDING 저장 한 번, FAILED 저장 한 번이다(`OrderService.placeOrder`).
- 그 사이에 HTTP 호출도 두 번 한다(product 행사 조회, inventory 재고 차감).
- 부하 없이 매진 응답만 받은 29건(2026-11-03, Docker 네트워크 안 `gateway:8080`)은 최소 5.7 / 중앙 6.4 / 최대 9.6ms 였다.
- 동시 5,000명일 때는 order-service 커넥션 10개를 모두가 나눠 쓴다.
  - 커넥션을 한 번 쥐는 시간은 평균 3.33ms(4차)~3.47ms(2단계)다. 부하가 없을 때는 1.6ms 였다.
  - 그래서 처리할 수 있는 양은 10 ÷ (2 × 약 3.4ms) ≈ 초당 1,450~1,500건이다.
  - 5,000건을 다 처리하려면 최소 3.3~3.5초가 걸린다. 측정한 p95 3.2~3.8초, rps 약 1,000~1,150 과 맞는다.
- 부하 때 커넥션을 쥐는 시간이 두 배가 되는 이유는, order-service 의 CPU 2개를 Tomcat 스레드 200개가 나눠 쓰기 때문으로 보인다. 측정 중 order-service CPU 는 최대 219% 였다. 확인하지는 않았다.

## 한계

- 군마다 8회라, "늘어진 실행이 몇 회 중 몇 번"은 흔들림이 크다. 넘침 건수(c 는 0~89, a·b 는 수천~1만6천)와 응답 대기의 계단 모양이 주 근거다.
- 표본기는 게이트웨이 cgroup 밖 컨테이너에서 돌렸지만 같은 Docker VM 의 CPU 를 쓴다. 진단 실행은 k6 요청별 csv 를 남겨 k6 의 일이 조금 늘었다.
- 첫 몰림에서 얼마나 넘치는지가 실행마다 왜 다른지는 확인하지 않았다(CPU 경쟁·JIT·GC 정지 시점으로 추정).
- 1단계 4차에는 넘침·swap 을 기록하지 않아서, 4차와 2단계의 차이는 설명하지 못한다.
