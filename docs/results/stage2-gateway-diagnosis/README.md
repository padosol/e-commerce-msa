# 2단계 게이트웨이 60초 타임아웃 원인 조사

2단계 매트릭스(`../stage2-summary.md` §4)에서 k6 요청이 60초 타임아웃에 걸린 실행이 4번 나왔다. 그중 3번이 `INCONCLUSIVE`(`order-total`)다.
타임아웃 난 요청은 주문이 생기지 않았고, 게이트웨이 504 도 없었다. 2026-11-03 19시대에 진단 실행 32회로 원인을 확인했다.

## 결론

- **원인은 게이트웨이의 연결 대기열(listen backlog) 100칸이다.** 연결 5000개가 같은 순간에 몰리면 이 대기열이 넘친다.
  - 넘치면 커널이 연결 요청(SYN)·연결 완료(ACK)·요청 데이터를 버린다(`ListenOverflows`).
  - 클라이언트(Linux TCP)는 버려진 패킷을 0.2초부터 대기 시간을 두 배씩 늘려 다시 보낸다.
  - 연결이 모두 같은 순간에 시작했으므로, 다시 보내는 시점도 6.2·12.6·25.4·51.0초에 한꺼번에 몰린다. 그때마다 대기열이 또 넘쳐, 한 번에 약 100~200건만 들어간다.
  - 51초에도 못 들어간 요청은 다음 재전송이 약 102초 뒤다. 그래서 k6 의 60초 타임아웃에 걸린다.
  - 이 요청들은 게이트웨이 애플리케이션에 닿지 않는다. 그래서 504 도 주문도 없다.
- **게이트웨이 swap 과 GC 정지는 꼭 있어야 하는 원인이 아니다.**
  - swap 을 없애도(아래 b) 8회 중 2회가 53초까지 늘어졌다.
  - 반대로 swap 과 1.4~1.6초 Full GC 를 그대로 두고 대기열만 4096칸으로 늘리자(c), 8회 모두 넘침이 거의 0이었고 늘어진 실행도 없었다.
- **실행마다 결과가 다른 이유:** 첫 몰림에서 대기열이 얼마나 넘치느냐에 달렸다. 넘침은 실행마다 0~16,850건으로 흔들렸고, 1.5만 건을 넘은 실행만 50초 이상 늘어졌다.
  - 넘침 양은 그 순간 게이트웨이가 연결을 얼마나 빨리 받아 가느냐에 달린 것으로 보인다. 게이트웨이는 CPU 2개를 Tomcat worker 200개·JIT·GC 와 나눠 쓴다.
  - 2단계(28회 중 5회)가 1단계 4차(28회 중 1회)보다 많았던 이유는 정하지 못했다. 같은 설정에서도 8회 중 0~2회로 흔들린다.
- **별개 문제: 게이트웨이가 swap 을 쓰고 있다.**
  - 640m 한도인데 JVM 이 약 800 MiB 를 쓴다. 그래서 약 300 MiB 가 swap 에 있다.
  - 그 결과 young GC 가 0.4~1.2초, Full GC 가 0.6~1.8초씩 멈춘다. swap 이 없으면 첫 실행을 빼고 둘 다 0.1초 안팎이다.
  - 이 정지는 지연을 키운다. 다만 타임아웃의 원인은 아니다.

## 근거

### 1. 늘어진 시간은 연결 단계가 아니라 응답 대기 단계에 있다

k6 요약(`runs/<RUN_ID>/k6-summary.json`)의 단계별 최댓값:

| 실행 | connecting 최대 | waiting 최대 | 응답 최대 |
|---|---|---|---|
| 20261103-171909-naive (2단계, 타임아웃 418) | 3.6s | 58.8s | 58.8s |
| 20261103-172314-conditional (2단계, 타임아웃 17) | 3.6s | 58.8s | 58.8s |
| 20261103-172949-optimistic-r2 (2단계, 타임아웃 26) | 2.1s | 58.8s | 58.8s |
| 20261103-155008-conditional (1단계 4차, 늘어진 유일한 실행) | 2.1s | 52.5s | 52.5s |
| 20261103-172116-naive (2단계, 정상) | 1.1s | 4.5s | 4.5s |

연결 단계 최대 1.1~3.6초는 연결 요청(SYN)을 다시 보낸 흔적이다. 정상 실행에도 있다.
수십 초 늘어진 부분은 모두 waiting(요청을 보낸 뒤 첫 바이트까지)에 있다.
대기열이 꽉 찬 상태에서 연결 완료(ACK)가 버려져도, 클라이언트는 연결된 줄 알고 요청을 보낸다. 그 요청을 다시 보내는 시간이 waiting 에 잡힌다.

### 2. 게이트웨이 대기열은 100칸이고 계속 넘친다

- `ss -ltn` 으로 본 게이트웨이 `*:8080` LISTEN 의 Send-Q(대기열 한도)는 100 이다. Tomcat `server.tomcat.accept-count` 기본값이다.
  컨테이너의 `net.core.somaxconn` 은 4096 이라 상한이 되지 않는다. syncookies 는 켜져 있다.
- 게이트웨이 컨테이너 안 `/proc/net/netstat` 누적값(2단계 매트릭스 끝): `ListenOverflows` 204,901, `TCPReqQFullDoCookies` 69,044, `SyncookiesRecv` 189,732.
- order-service 의 `*:8084` 도 100칸이지만 `ListenOverflows` 는 0 이다. 게이트웨이가 order-service 에 연결 풀로 붙어서, 연결이 한꺼번에 몰리지 않는다.
- 진단 실행의 0.25초 표본(`tools/timeline.sh`)에서 넘침은 k6 시작 직후(연결 5000개 몰림)와 약 1초 뒤(SYN 재전송)에 몰린다.

### 3. 응답 대기 시간이 재전송 시점에 계단처럼 몰린다

`waiting-histogram.txt` 에서 50초 이상 늘어진 3회와 정상 1회만 옮긴다(구간 시작 초: 건수).

| 실행 | 0~3.5초 | 6.5초 | 13초 | 26초 | 52~53초 | 58초(타임아웃) |
|---|---|---|---|---|---|---|
| a8 | 4,306 | 184 | 150 | 193 | 110 | 57 |
| b1 | 4,282 | 308 | 139 | 136 | 135 | – |
| b2 | 4,482 | 204 | 159 | 119 | 36 | – |
| b3 (정상) | 5,000 | – | – | – | – | – |

4~6초, 7~12초, 14~25초, 27~51초 구간은 비어 있다.
재전송은 0.2초에서 시작해 두 배씩 늘므로 누적 시점이 6.2·12.6·25.4·51.0초다. 계단이 정확히 그 자리에 있다.
계단 하나에 들어간 요청은 약 100~200건으로, 대기열 100칸에 그 사이 게이트웨이가 받아 간 만큼을 더한 수다.
a8 은 51초에도 57건이 남았다. 이 57건은 다음 시점(약 102초)을 기다리다 k6 타임아웃에 걸렸다. 주문 수도 4,943건으로 정확히 57건이 모자랐다.

2단계 매트릭스에서도 같은 모양이었다. k6 원격 기록(5초마다 보냄)으로 본 응답 완료 시각(k6 시작 기준)은 이렇다.
- 171909: +6, +10, +17, +29, +55~56초, 그리고 +60초 타임아웃 418건
- 172314: +6, +10, +16~17, +30, +56초, 그리고 +62초 타임아웃 17건

### 4. 게이트웨이는 swap 중이다 (별개 문제)

2단계 매트릭스 뒤 각 컨테이너의 cgroup 값:

| 컨테이너 | 메모리 한도 | swap 사용 | swap 에서 다시 읽은 anon page | 메모리 한도 도달 | major fault |
|---|---|---|---|---|---|
| gateway | 640 MiB | 247 MiB | 1,484,652 | 54,617 | 924,722 |
| order-service | 1 GiB | 0 | 0 | 0 | 6 |
| payment-service | 640 MiB | 0 | 0 | 0 | 0 |
| product-service | 640 MiB | 0 | 0 | 0 | 0 |

- Docker VM 의 swap 파일(1 GiB)에서 쓰인 254 MiB 는 거의 다 게이트웨이 몫이다.
  Docker 는 `--memory` 만 주면 같은 크기의 swap 을 더 허용한다(`memory.swap.max` = 640 MiB).
- JVM 이 보고하는 메모리는 heap 433 MiB 와 non-heap 92 MiB 다. 그런데 프로세스는 RSS 628 MiB 에 swap 170 MiB 로, 약 800 MiB 를 쓴다.
  heap 이 컨테이너의 70%(448 MiB)라, 나머지 192 MiB 로는 스레드 스택·JIT·GC·네이티브 메모리를 다 담지 못한다.
- 새로 만든 게이트웨이도 첫 실행부터 swap 이 300 MiB 를 넘었다(a1).

## 실험: 한 번에 하나씩 바꿔 본 게이트웨이

모든 진단 실행은 `tools/diag-run.sh` 로 돌렸다. 단계는 `scripts/run-test.sh` 와 같다.
- 데이터 초기화, 재고 100, 토큰 5000개, 같은 k6 스크립트와 k6 컨테이너 한도(cpus 4 / 2g)
- inventory 전략은 naive
- 결과는 `docs/results` 표에 넣지 않았다

r 을 뺀 각 군은 게이트웨이를 새로 만든 뒤 smoke 1회를 하고 8회 돌렸다. 바꾼 설정은 `tools/*-override.yaml` 이다(`docker compose -f compose.yaml -f <override> up -d gateway`).
실험 뒤에는 `compose.yaml` 그대로 게이트웨이를 다시 만들었다. 대기열 100, 640M, Serial GC, `JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=70` 인 것을 확인했다.

| 군 | 게이트웨이 설정 | 대기열 넘침 | swap 최대 | young GC 최대 | Full GC 최대 | 응답 최대 | 50초 넘게 늘어진 실행 | 주문 누락 |
|---|---|---|---|---|---|---|---|---|
| r | 2단계 매트릭스 뒤 그대로 (640m, heap 448 MiB, 대기열 100) | 0~5,963 | 285~320 MiB | 644~1,248ms | 806~1,120ms | 4.0~7.3s | 0/8 | 0 |
| a | 원래 설정, 새 컨테이너 | 3,313~16,850 | 302~346 MiB | 358~924ms | 1,630~1,822ms | 3.3~58.8s | 1/8 (a8) | 57 (a8) |
| b | 메모리 1g + `-Xmx448m` (heap·GC 같음, swap 압박만 없앰) | 219~16,588 | 0 | 69~620ms (첫 실행 620, 나머지 69~130) | 86~101ms | 2.9~53.4s | 2/8 (b1, b2) | 0 |
| c | 원래 설정 + `SERVER_TOMCAT_ACCEPTCOUNT=4096` (대기열만 늘림) | 0~89 | 140~336 MiB | 527~830ms | 1,413~1,566ms | 4.4~6.4s | 0/8 | 0 |

실행별 값은 `runs-summary.txt` 에 있다. GC 열은 Prometheus 1초 표본이다. 원본 표본은 `runs/<이름>/` 에 있다.
- `gw.txt`: 게이트웨이 카운터 0.25초 표본
- `k6-summary.json`, `order-stats.json`, `times.txt`
- `req.csv.gz`: k6 요청별 값. a8·b1·b2·c8 만 남겼다

b 에서 swap 을 없애자 GC 정지는 10분의 1로 줄었다. 그래도 대기열 넘침과 50초 늘어짐은 남았다.
c 에서는 swap 과 긴 GC 가 그대로인데 넘침과 늘어짐이 사라졌다. 그래서 타임아웃을 결정하는 것은 대기열 크기다.

c 에서는 요청이 버려지지 않고 모두 바로 들어와, 응답 대기가 0~6초에 고르게 퍼졌다.
p99 는 4.4~6.3초로, 같은 swap 상태인 a 의 늘어지지 않은 실행(3.1~6.7초)과 겹친다.
지금까지 요청 일부는 TCP 재전송 속에서 줄을 서고 있었다. 대기열을 늘리면 그 줄이 게이트웨이와 order-service 안으로 옮겨 온다.
그래서 대기열 크기를 바꾸면 끝단 지연의 분포가 달라질 수 있다. 바꾼다면 0~2단계와 비교할 기준을 새로 잡아야 한다.

## 한계

- 군마다 8회라, "늘어진 실행이 몇 회 중 몇 번"은 흔들림이 크다. 넘침 건수(c 는 0~89, a·b 는 수천~1만6천)와 응답 대기의 계단 모양이 주 근거다.
- 표본기는 게이트웨이 cgroup 밖 컨테이너에서 돌렸지만 같은 Docker VM 의 CPU 를 쓴다. 진단 실행은 k6 요청별 csv 를 남겨 k6 의 일이 조금 늘었다.
- 첫 몰림에서 얼마나 넘치는지가 실행마다 왜 다른지는 확인하지 않았다(CPU 경쟁·JIT·GC 정지 시점으로 추정).
- 1단계 4차에는 넘침·swap 을 기록하지 않아서, 4차와 2단계의 차이는 설명하지 못한다.
