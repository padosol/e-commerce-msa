# 1단계 5차 요약: 부하 조건을 "1초 동안 500명" 으로 바꾼 뒤

부하 조건을 현실에 가깝게 바꾼 뒤 1단계 세 방식을 다시 쟀다.
- 이전: 5000명이 같은 순간에 요청
- 이번: 500명이 1초 동안 같은 간격으로 요청, 재고 100
- 앱 설정: 1단계 고정 설정 그대로(모든 앱 640 MiB, Serial GC)

7개 구성마다 워밍업 1회 뒤 측정 3회를 돌렸다(2026-11-03 22:10~22:13). 환경은 `stage1-attempt5-environment.md` 에 있다.
1단계 4차(5000명 동시 요청)의 해석은 `stage1-summary.md` 에 그대로 둔다. 두 측정은 부하 조건이 달라 숫자를 직접 비교하지 않는다.

**한 줄 결론:**
- 세 방식 모두 초과 판매를 막았다. 18회 모두 `OK`, 재고 100개를 정확히 다 팔았다. naive 는 3회 모두 `OVERSOLD`(paid 408~439)다.
- 4차와 달리 앞단(order-service 커넥션 풀)이 포화되지 않는다. 그래서 방식마다의 비용이 끝단 p95 에 그대로 드러났다.
  - 낙관적 락 238~246ms < 조건부 UPDATE 264ms < 비관적 락 285ms
- 순서는 "매진된 뒤의 요청도 행 락을 잡느냐" 로 설명된다. 비관적 락은 500건 모두 트랜잭션 동안 락을 쥐고, 조건부 UPDATE 는 500건 모두 문장 하나 동안 락을 잡는다. 낙관적 락은 재고가 남아 있을 때만 갱신을 시도한다.
- `INCONCLUSIVE` 0회, 타임아웃 0건, 게이트웨이 연결 대기열 넘침 0건이다.

## 1. 정확성

- 정확한 6개 구성 18회가 모두 `OK` 다(paid 100, undersold 0).
- naive 는 3회 모두 `OVERSOLD` 다. paid 는 408 / 426 / 439 다.
  요청이 2ms 간격으로 퍼져도 결제 처리(약 200ms) 동안 수십 건이 겹친다. 그래서 같은 재고를 읽고 차감하는 일이 계속 생긴다.
- 낙관적 락은 재시도가 없으면(r0) 측정 3회의 최종 충돌(`STOCK_CONFLICT`)이 각각 187 / 92 / 77건이었다.
  재고가 남아 있던 때 충돌로 거절된 요청이지만, 뒤에 온 사용자들이 재고를 가져가 결국 100개가 다 팔렸다.
  재시도를 늘리면 충돌로 거절되는 사용자가 줄었다(중앙값 r1 34, r2 15, r3 12건). 대신 재시도가 그만큼 늘었다(70 / 96 / 120회).

## 2. 비용: 방식마다 끝단 지연이 달라졌다

| 구성 | 끝단 p95 중앙값 | 3회 범위 | inventory 차감 서버 p95 | MySQL 행 락 대기 (평균) | order 커넥션 대기 평균 | order Hikari pending 최대 |
|---|---|---|---|---|---|---|
| naive | 751ms | 531~1,048ms | 16.5ms | 351회 (3.19ms) | 34.4ms | 67 |
| 비관적 락 | 285ms | 275~352ms | 13.1ms | 261회 (2.62ms) | 5.9ms | 22 |
| 조건부 UPDATE | 264ms | 253~307ms | 14.0ms | 105회 (4.53ms) | 2.9ms | 0 |
| 낙관적 락 r0 | 246ms | 239~646ms | 4.3ms | 89회 (1.29ms) | 0.06ms | 0 |
| 낙관적 락 r1~r3 | 238~240ms | 227~246ms | 4.1~6.0ms | 103~131회 (1.12~1.18ms) | 0.01~0.1ms | 0 |

이 p95 가 무엇을 재는지 먼저 짚는다. 요청 500건 중 400건은 수 ms 에 끝나는 매진 응답이고, 100건만 결제(약 200ms)까지 간다.
그래서 전체 p95(느린 쪽 25번째)는 결제한 100건 안쪽의 값이다. 결제 시간이 같으니, 구성 사이 차이(238 → 264 → 285ms)는 그 앞 단계(재고 차감과 그 앞의 줄)에서 더해진 지연이다.
rps 는 naive(343)와 비관적 락(477)을 빼면 약 496 으로, 도착 속도(초당 500)를 따라갔다.

**왜 이 순서인가.** 차이는 매진된 뒤의 요청에서 난다(`inventory-service/.../stock/*StockStrategy.java`).
- **비관적 락:** 모든 요청이 트랜잭션 안에서 `SELECT ... FOR UPDATE` 로 행 락을 잡는다. 비교·갱신·커밋이 끝날 때까지 쥐고 있다. 매진 뒤에도 락을 잡은 다음 `OUT_OF_STOCK` 을 돌려준다.
  - 그래서 500건이 한 줄로 선다. 락 대기는 261회로 가장 많다.
  - inventory 가 늦게 답하니 order-service 커넥션도 오래 잡힌다(pending 최대 22, 대기 평균 5.9ms).
- **조건부 UPDATE:** 모든 요청이 `UPDATE ... WHERE quantity >= ?` 를 실행한다. 0건 갱신이어도 문장이 도는 동안 행 락을 잡는다.
  - 그래서 500건 모두 락을 거친다. 다만 문장 하나 동안만 잡으므로 비관적 락보다 짧다(락 대기 105회).
- **낙관적 락:** 락 없이 읽고, 재고가 남아 있을 때만 `UPDATE ... WHERE version = ?` 를 시도한다. 매진 뒤 요청은 읽기만 하고 끝나 락을 잡지 않는다.
  - 그래서 inventory 차감이 가장 빠르다(서버 p95 약 4~6ms). order-service 에도 줄이 생기지 않는다.
  - 재시도 횟수(r0~r3)는 끝단 지연에 거의 영향이 없었다(238~246ms).
- **naive:** 락이 없는데도 가장 느리다. 초과 판매로 결제가 426건 일어나기 때문이다(다른 구성은 100건).
  - 결제마다 약 200ms 씩 order-service 스레드와 커넥션을 쥔다. 그래서 order-service 에 줄이 생긴다(pending 최대 67, 대기 평균 34ms).

## 3. 튄 실행

- **optimistic-r0 첫 측정(20261103-221154):** p95 646ms 로, 같은 구성의 다른 두 회(239·246ms)보다 400ms 쯤 느렸다.
  - 서버 쪽 값은 거의 같았다. 게이트웨이 서버 측 p95 255ms(다른 회 243ms), order-service 평균 58ms(50ms), 결제 평균 203ms(202ms), inventory 차감 평균 2.3ms(1.3ms).
  - 늘어난 시간은 k6 의 waiting(요청을 보낸 뒤 첫 바이트까지)에 있다. 연결 단계는 최대 27ms 로 정상이고, 게이트웨이 대기열 넘침도 매트릭스 내내 0 이다.
  - 그래서 게이트웨이가 요청 처리를 시작하기 전, 또는 k6 쪽에서 생긴 지연으로 보인다. 원인은 확인하지 못했다.
  - 후보 하나는 게이트웨이 swap 이다. 이 조건에서도 swap 을 286 MiB 쓰고, 메모리 한도에 1,642번 닿았다. 다만 실행 단위로 기록하지 않아 이 실행과 맞춰 보지 못했다.
- **각 구성의 첫 측정이 아직 덜 데워져 있다.**
  - naive 첫 측정(221035)은 order 커넥션 대기 평균이 120ms, 비관적 락 첫 측정(221102)은 50ms 였다. 나머지 두 회는 3.9~34ms 다.
  - 워밍업 1회가 이제 요청 500건이라, 4차(5000건)보다 JVM 을 덜 데운다. 구성을 바꿀 때마다 inventory-service 를 새로 만들기 때문에 영향이 더 크다.
  - 중앙값은 이 영향을 줄이지만, 범위(p95 범위 열)에는 남아 있다.

## 4. 4차(5000명 동시)와 무엇이 달라졌나

- **4차:** 모든 구성에서 order-service 앞단이 포화됐다(Tomcat 200, Hikari pending 약 185). 그래서 끝단 p95 가 구성과 관계없이 3~4초였고, 방식 차이는 inventory 서버 p95 에만 남았다.
- **5차:** 앞단이 포화되지 않는다(정확한 구성의 order Hikari pending 0~22). 그래서 행 락을 얼마나 오래, 얼마나 많이 잡느냐가 끝단 지연에 그대로 드러났다.
- **naive:** 두 조건 모두 초과 판매했다. 이 실험이 다룰 문제(동시 주문의 정합성)는 새 조건에서도 그대로 재현된다.
