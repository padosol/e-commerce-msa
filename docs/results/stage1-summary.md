# 1단계 요약: DB 수준 재고 차감 3방식 비교

1단계의 질문은 **"정확해진 대신 얼마나 느려지나, 그리고 왜 느려지나"** 였다.
조건은 USERS 5000, 재고 100이다. 4차 측정(2026-11-03 15:48~15:54)에서 7개 구성마다 워밍업 1회 뒤에 측정 3회를 돌렸다.
워밍업은 비교에서 뺐고, 아래 값은 측정 3회의 중앙값이다. `INCONCLUSIVE` 가 한 번도 없어서 빼거나 다시 잰 실행은 없다.
4차는 k6 를 Docker 네트워크 안 컨테이너로 돌려 게이트웨이에 직접 연결했다(측정 메모). 1~3차 기록과 2차 기준의 이전 요약은 `stage1-attempt1/`~`stage1-attempt3/` 에 보관했다.
실행별 원본은 `runs/<RUN_ID>/` 에 있고, 표는 `scripts/summarize.sh` 로 다시 만들 수 있다.

**한 줄 결론:** 세 방식 모두 초과 판매를 막았다(18회 모두 `OK`, 재고 100개를 정확히 다 팔았다). 끝단(k6)에서는 naive 와 구분될 만큼 느려지지 않았다. 구성 사이 차이가 같은 구성 3회 사이 편차보다 작다.
기록에서 모든 구성에 똑같이 줄이 보이는 곳은 재고 행이 아니라 앞단(gateway·order-service)이다. 한 행 구조의 비용은 재고·DB 계층(낙관적 락 충돌·재시도, 행 락 대기)에만 숫자로 남았다.
그래서 이번 기록만으로는 "DB 한 행에 몰리는 구조의 한계"를 2단계의 근거로 내세울 수 없다.

## 1. 정답

- **naive**: 3회 모두 `OVERSOLD` 였다. 재고 100에 534/540/508개가 팔렸다(중앙값 534, 재고의 약 5.3배).
  `verify.json` 의 stockMismatch 는 -434/-440/-408 이다. 재고는 100만 줄었는데 그보다 434/440/408건 더 팔렸다는 뜻으로, lost update 다.
- **pessimistic·conditional·optimistic-r0~r3**: 18회 모두 `OK`, paid 100이었다.
  18회의 `verify.json` 은 모두 finalStock 0, stockMismatch 0, pending 0, 주문 전 실패 0이다. 재고 100개를 남김없이, 넘치지 않게 팔았다.
- **덜 팔림과 타임아웃은 한 번도 없었다.** 18회 모두 undersold 0, timeouts 0(6개 계층 모두 0)이다.
  - 가장 느린 요청은 52514.94 ms(`20261103-155008-conditional` 의 k6 max)로, k6 요청 타임아웃 60s 에 닿지 않았다. 이 실행은 2절에서 따로 본다.
  - 이 실행을 빼면 가장 느린 요청은 6655.84 ms(`20261103-155217-optimistic-r1`)였다.
- **낙관적 락 충돌은 판매량을 줄이지 않았다.**
  - 최종 CONFLICT 중앙값은 r0 500 → r1 369 → r2 255 → r3 187로, 재시도가 늘수록 줄었다(r0 대비 r3 약 63% 감소).
  - 충돌 자체(`causes.json` 의 optimistic.conflicts)는 r0 493~520, r1 784~834, r2 856~896, r3 841~900회로 오히려 늘었다. 실행마다 충돌 = 재시도 + 최종 CONFLICT 다(예: `20261103-155403-optimistic-r3` 900 = 709 + 191).
  - 그래도 판매는 늘 100이었다. 같은 실행들에서 품절(`SOLD_OUT`) 응답이 4380~4732건 나왔기 때문이다(각 실행 `verify.json` 의 failedByReason).
  - 재고가 0이 된 뒤에도 요청이 계속 들어왔다는 뜻이다. 충돌로 떨어진 요청의 몫은 뒤에 온 요청이 사 갔다.
  - 5000명이 100개를 두고 다투는 이 조건에서는 충돌이 덜 팔림으로 이어질 여지가 없었다.

설계는 덜 팔림·타임아웃을 "방식의 특성"으로 기록할 준비를 했다. 하지만 이번 조건에서는 둘 다 나오지 않아, "왜 덜 팔렸나"는 설명할 대상이 없다.

**끝단(k6), naive 대비 (중앙값):**
- naive 는 p95 3640.36 ms, p99 3736.57 ms, rps 1008.86 이었다.
- 정확한 6개 구성의 p95 는 2671.92(r0)~4544.07(r3) ms 다. naive 보다 낮은 것이 넷(r0, conditional, r1, pessimistic), 높은 것이 둘(r2 +54.01, r3 +903.71 ms)이다.

**실행 사이 편차는 연결 단계 시간과 함께 움직였다** (각 실행 `k6-summary.json`)

  실행별로도 r1~r3 9회(8.55~70.5 ms)가 모두 r0 3회(2.27~3.08 ms)보다 크다. 다만 r2 가 r3 보다 커서, 재시도 횟수에 비례한다고까지는 말할 수 없다.
- 이번 기록에서 정확해진 대가가 "시간"으로 분명하게 드러난 곳은 여기다. 그래도 끝단 p95 의 많아야 약 2%(r2: 66.64 / 3694.37 ms = 1.8%)다.

**결제 호출 차이 (naive):**
- naive 는 결제 호출이 534회(중앙값, 실행별 508~540), 나머지는 100회다.
- 결제 1회에는 설정상 200 ms ± 50 ms 지연이 들어간다(각 `report.md` 의 payment 설정 `delayMs 200, jitterMs 50`). 따라서 naive 는 결제까지 가는 긴 경로가 약 5배 많다.
- 그런데도 naive 의 끝단 p95 는 정확한 구성들 사이에 있다. 2차 측정(호스트 k6) 요약에서는 naive 가 6개 구성 모두보다 p95 가 높았는데, 4차에서는 그렇지 않다.
- 결제 경로의 몫이 끝단에 얼마나 섞였는지는 기록으로 나눌 수 없다.

## 3. 원인

계획이 예상한 사슬은 "행 락 대기 → 커넥션 풀 대기 → Tomcat 포화 → 지연·덜 팔림"이었다. 기록은 다르게 말한다.

**앞단이 모든 구성에서 똑같이 포화됐다** (보조 표, 각 `causes.json`)
- order-service Tomcat busy 최대는 측정 21회 중 20회가 200, 1회가 199(`20261103-154914-pessimistic`)다. Tomcat 기본 최대 스레드 수 200에 닿았다.
- order-service Hikari pending 최대는 21회 모두 181~187 이다. gateway Tomcat busy 최대는 구성별 중앙값 193~200 이다. naive 도 같다.
- k6 진행 로그(1초 간격, 시작 구간과 꼬리 제외)의 초당 완료 수도 구성별 평균 1146(naive)~1301(r0)건으로 비슷했다.
- 요청은 order-service 앞에서 줄을 섰고, 이 줄은 재고 차감 방식과 상관이 없었다.
- 정확한 방식에서는 5000건 중 4900건이 결제 없이 끝난다(품절 또는 충돌). 결제를 거친 요청은 100건뿐이다.
  그러니 p95 이상 걸린 약 250건(5000건의 5%) 가운데 최소 150건은 결제를 거치지 않은 요청이다.
- 즉 실행마다 결제 없는 짧은 경로의 요청이 최소 150건, 그 실행의 p95(구성별 중앙값 2.7~4.5초) 이상 걸렸다.
  차감 서버 시간(실행별 많아야 70.5 ms)으로는 설명되지 않으므로, 대부분은 기다린 시간으로 보인다.
- 다만 order-service 안의 구간별 시간은 기록되지 않았다. 그래서 정확히 어디서 몇 초를 기다렸는지는 나눌 수 없다.

**order-service 가 왜 그만큼 DB 커넥션을 기다렸는지는 기록으로 나눌 수 없다.**
- 풀 크기(Hikari 기본값) 때문인지 MySQL 처리 시간 때문인지 가르려면 order-service DB 질의 시간이나 MySQL CPU 가 있어야 하는데, 기록되지 않았다.
- 다만 재고 행 락 경합이 원인이라는 근거는 없다. 락 대기가 적은 conditional(230회)과 많은 pessimistic(1870회)의 order Hikari pending 이 186과 185로 같고, naive(470회)도 185다.

**재고 쪽은 대체로 포화되지 않았다.**
- r3 를 뺀 6개 구성은 inventory Tomcat busy 최대 중앙값이 2~7, inventory Hikari pending 최대 중앙값이 0이다.
- inventory 쪽 줄이 기록된 측정은 21회 중 4회다. r3 는 3회 중 2회라 중앙값이 120 / 131 이 됐다.
  - `20261103-154923-pessimistic`: Hikari pending 146, Tomcat busy 158
  - `20261103-155312-optimistic-r2`: 115 / 125
  - `20261103-155343-optimistic-r3`: 120 / 131
  - `20261103-155354-optimistic-r3`: 133 / 149
- 이 4회의 끝단 p95 는 그 구성에서 가장 높기도(154923 4973.6, 155343 4889.62 ms), 가장 낮기도(155312 2872.98, 155354 3394.72 ms) 했다. inventory 의 줄과 끝단 지연은 같이 움직이지 않았다.
- MySQL 현재 락 대기 수는 21회에서 많아야 9였다(`causes.json` 의 maxCurrentWaits, `20261103-155230-optimistic-r1`·`20261103-155403-optimistic-r3`). 표본 시점마다 한 행을 두고 동시에 기다린 요청은 한 자릿수였다.
- 이 최댓값들은 1s 표본이고 실행이 4~9초라(`report.md` 의 테스트 소요 시간), 실행마다 표본이 몇 개뿐이다. 순간 최댓값은 놓쳤을 수 있다.

**락 대기는 있었지만 짧았다.**
- pessimistic 은 락 대기 1870회(실행별 1840~2241회, 차감 5000건의 37~45%)로 naive 470회의 약 4배였고, 평균 0.88 ms 였다.
- conditional 은 230회로 pessimistic 의 약 1/8 이지만, 평균 5.88 ms 로 한 번 기다릴 때 약 6.7배 길었다. 2차 측정에서도 같은 방향이었다. 왜 이런 차이가 나는지는 기록된 지표로 설명할 수 없다.
- 실행별 누적 락 대기 시간(`lockTimeMs`)은 21회 모두 789~2528 ms 다. 5000건 전체를 합한 값이라, 요청 1건당 평균으로는 많아야 약 0.5 ms 다.

**재시도는 재고 쪽 비용을 키웠지만 끝단에는 분명하게 드러나지 않았다.**
- 재시도 총횟수는 r1 435, r2 622, r3 702다.
- 같은 구간에서 차감 서버 p95 는 r0 2.6 ms → 12.8 / 66.64 / 37.66 ms 가 됐고, r3 는 3회 중 2회에서 inventory 커넥션 풀 대기가 생겼다.
- r3 는 끝단 p95 중앙값이 7개 구성 중 가장 높다(4544.07 ms). 재시도 비용이 끝단에 드러나기 시작한 신호일 수 있다.
- 하지만 r3 의 p95 범위(3394.72~4889.62)는 naive(3542.47~5200.36)와 겹친다. 또 inventory 줄이 가장 컸던 `20261103-155354-optimistic-r3` 가 r3 에서 p95 가 가장 낮았다. 그래서 기록으로는 확인할 수 없다.

**덜 팔림·타임아웃은 설명할 사슬이 없다.** 한 번도 나오지 않았기 때문이다.

## 4. 2단계로 넘어갈 근거

**이번 기록으로는 "DB 한 행에 몰리는 구조 자체의 한계"가 끝단 지연의 원인이라고 말할 수 없다.**
- 끝단 p95 2672~4544 ms(중앙값) 가운데 재고 차감 서버 시간은 1~66.64 ms(중앙값)로, 많아야 약 2%다.
- 재고 서비스는 r3 를 빼면 대체로 포화되지 않았다(Tomcat busy 중앙값 2~7, Hikari pending 중앙값 0). 행 앞의 동시 대기도 많아야 9건이었다.
- 같은 때 order-service 는 Tomcat busy 최대 199~200(한도 200), Hikari pending 181~187, gateway 는 Tomcat busy 중앙값 193~200 으로, 방식과 무관하게 먼저 차 있었다. naive 도 같았다.
- 끝단 p95 는 같은 구성 안에서 1.4~2.4초 흔들렸고(conditional 제외, 구성 사이 차이는 많아야 1.9초), 그 흔들림의 일부는 연결 단계 시간과 함께 움직였다. 끝단 숫자에는 방식이 아닌 측정 경로의 몫도 섞여 있다.
- 따라서 pessimistic·conditional·r0 의 차감(1~3.74 ms)을 더 빠른 저장소로 옮겨도, 끝단 수 초에서 줄어들 몫은 작아 보인다(추정).

**한 행 구조의 비용이 숫자로 남은 곳은 DB·재고 계층이다.**
- 낙관적 락 r0 에서는 5000건 중 500건(10%)이 충돌로 실패했다.
- 재시도로 r3 에서 187건까지 줄었지만, 차감 서버 p95 는 r0 의 약 14배(2.6 → 37.66 ms)가 됐고, r3 3회 중 2회에서 inventory Hikari pending(커넥션 대기)이 120·133 까지 올라갔다.
- pessimistic 은 차감 5000건에 락 대기 1870회를 냈다.
- 이 비용들은 실제로 있지만, 이번 조건에서는 앞단 포화에 가려 끝단까지 분명하게 올라오지 않았다.

**기록이 가리키는 것 (판단은 사용자 몫):**
- 이번 조건에서 끝단을 정한 것은 order-service 앞의 줄이다. Tomcat 200 스레드가 모두 찼고, DB 커넥션을 약 185개가 기다렸다. 이 줄이 왜 생겼는지(풀 크기인지, MySQL 처리 시간인지)는 기록되지 않았다.
- 한 행 구조의 한계를 끝단 숫자로 보려면, 재고 쪽이 앞단보다 먼저 포화되는 조건이 필요하다. 그러려면 부하 규모나 고정 설정(Tomcat/Hikari 기본값)을 바꿔야 하는데, 둘 다 1단계 범위 밖이다.
- 지금 조건 그대로 2단계를 재면, 끝단 지표로는 1단계와 구분하기 어려울 수 있다(추정).
- 2단계로 갈 근거를 "한 행 경합"에 둘지, 다른 데(예: order-service 앞의 줄)에 둘지는 이 결과를 보고 정할 일이다.

  - k6 컨테이너는 1초 표본 72개에서 CPU 최대 166%(한도 400%), 메모리 최대 1036 MiB(한도 2g)로 한도에 닿지 않았고, OOM 종료도 없었다. 이 표본은 실행별로 나뉘어 있지 않아, 이상 실행 중의 k6 상태를 따로 볼 수는 없다.
  - 28회 모두 k6 응답 합계 5000, 연결 단계 오류(`k6-unclassified`) 0건이다.
  - 연결 오류는 없어졌지만 연결 지연은 남았다. 측정 21회 중 15회의 연결 시간 p95 가 약 1~3초였다(2절). k6 의 p95·p99 에는 이 시간이 들어가지 않는다.
  - rps 는 5000 ÷ 실행 시간이라, 마지막 요청이 늦게 끝난 실행에서 낮게 나온다(2절의 이상 실행과 꼬리 실행).
- **비교 범위:** k6 가 이제 측정 대상과 같은 Docker VM 자원을 나눠 쓴다. 그래서 4차의 끝단 수치는 0단계나 1~3차(호스트 k6)와 바로 비교할 수 없다. naive 도 같은 방식으로 다시 쟀으므로 1단계 안의 비교는 유지된다.
- **Prometheus 값:** Hikari·Tomcat·현재 락 대기·서버 p95 는 1s 표본 값이다. 4차 측정 21회에는 `n/a` 가 없다.
