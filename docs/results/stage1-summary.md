# 1단계 요약: DB 수준 재고 차감 3방식 비교

1단계의 질문은 **"정확해진 대신 얼마나 느려지나, 그리고 왜 느려지나"** 였다.
조건은 USERS 5000, 재고 100이다. 7개 구성마다 워밍업 1회 뒤에 측정 3회를 돌렸다. 워밍업은 비교에서 뺐고, 아래 값은 측정 3회의 중앙값이다.
실행별 원본은 `runs/<RUN_ID>/` 에 있고, 표는 `scripts/summarize.sh` 로 다시 만들 수 있다.

**한 줄 결론:** 세 방식 모두 초과 판매를 막았다(18회 모두 `OK`). 그런데 끝단(k6) 기준으로는 naive 보다 느려지지 않았다.
기록에서 일관되게 줄이 보이는 곳은 재고 행이 아니라 앞단(gateway·order-service)이고, 이 포화는 방식과 무관하게 같았다.
그래서 이번 기록만으로는 "DB 한 행에 몰리는 구조의 한계"를 2단계의 근거로 내세울 수 없다.

## 1. 정답

- **naive**: 3회 모두 `OVERSOLD` 였다. 재고 100에 653/582/609개가 팔렸다(중앙값 609, 재고의 약 6배).
- **pessimistic·conditional·optimistic-r0~r3**: 18회 모두 `OK`, paid 100이었다. 18회의 `verify.json` 은 모두 finalStock 0, stockMismatch 0, pending 0이다.
- **덜 팔림과 타임아웃은 한 번도 없었다.** 18회 모두 undersold 0, timeouts 0이다.
  선택한 21회 중 가장 느린 요청도 9503 ms(`20261102-230103-pessimistic` 의 k6 max)였다. 어느 계층의 타임아웃(10s / 30s / 60s)에도 닿지 않았다.
- **낙관적 락 충돌은 판매량을 줄이지 않았다.** 최종 CONFLICT 중앙값은 r0 505 → r1 362 → r2 256 → r3 186으로, 재시도가 늘수록 줄었다(r0 대비 r3 63% 감소).
  그래도 판매는 늘 100이었다. 같은 실행들에서 품절(`SOLD_OUT`) 응답이 4393~4721건 나왔기 때문이다(각 실행 `verify.json`).
  재고가 0이 된 뒤에도 요청이 계속 들어왔다는 뜻이다. 충돌로 떨어진 요청의 몫은 뒤에 온 요청이 사 갔다.
  5000명이 100개를 두고 다투는 이 조건에서는 충돌이 덜 팔림으로 이어질 여지가 없었다.

설계는 덜 팔림·타임아웃을 "방식의 특성"으로 기록할 준비를 했다. 하지만 이번 조건에서는 둘 다 나오지 않았다.

## 2. 비용

**끝단(k6), naive 대비:**
- naive 는 p95 7354.19 ms, p99 8549.17 ms, rps 571.72였다.
- 정확한 방식 6개 구성의 p95 는 4778.39(r1)~6117.84(conditional) ms 로, 모두 naive 보다 1.2~2.6초 낮았다.
- p99 도 4984.29(r2)~7107.32(pessimistic) ms 로 모두 naive 보다 낮았다.
- rps 는 524.35(pessimistic)~961.92(r2)였다. naive 보다 낮은 것은 pessimistic 하나뿐이다.
- 즉 "정확해진 대신 느려졌다"는 끝단 수치에 나타나지 않았다.

**이 비교는 naive 쪽으로 기울어 있다.**
- naive 는 결제 호출이 609회(중앙값), 나머지는 100회다.
- 결제 1회에는 설정상 200 ms ± 50 ms 지연이 들어간다(각 `report.md` 의 payment 설정 `delayMs 200, jitterMs 50`).
- 따라서 naive 는 결제까지 가는 긴 경로가 약 6배 많다. 끝단이 naive 에서 더 느린 데에는 이 몫이 섞여 있을 수 있다.
- 다만 이 몫이 끝단 차이의 얼마인지는 기록으로 나눌 수 없다.

**서버 측 차감 시간(inventory 차감 p95):**
- naive 는 8.13* ms, pessimistic 2.98 ms, conditional 2.41 ms, r0 3.63 ms 였다. 차감 자체도 naive 보다 느려지지 않았다.
- 재시도가 붙으면 r1 16.84 ms, r2 53.38 ms, r3 41.59 ms 로 r0 의 4.6~14.7배가 된다.
- 이번 기록에서 정확해진 대가가 "시간"으로 드러난 곳은 여기뿐이다. 그래도 끝단 p95 의 많아야 약 1%(r2: 53.38 / 4869.94 ms)다.

**구성 사이 차이보다 실행 사이 편차가 크다.**
- 6개 구성의 p95 중앙값은 서로 많아야 1339 ms 차이다(4778.39~6117.84).
- 한 구성 안 3회의 p95 는 최대 3104 ms 벌어졌다(r2: 4552.72~7656.5). pessimistic 도 2158 ms 벌어졌다(5023.84~7182.33).
- 그래서 3회로는 6개 구성의 끝단 순위를 매길 수 없다.
- "pessimistic 이 conditional 보다 느릴 것"이라는 예상도 끝단에서는 확인되지 않았다(p95 6045.63 vs 6117.84).

## 3. 원인

계획이 예상한 사슬은 "행 락 대기 → 커넥션 풀 대기 → Tomcat 포화 → 지연·덜 팔림"이었다. 기록은 다르게 말한다.

**앞단이 모든 구성에서 똑같이 포화됐다** (보조 표)
- order-service Tomcat busy 최대는 7개 구성 모두 200이다. Tomcat 기본 최대 스레드 수 200에 닿았다.
- order-service Hikari pending 최대는 182~189, gateway Tomcat busy 최대는 195~200이다. naive 도 같다.
- 요청은 order-service 앞에서 줄을 섰고, 이 줄은 재고 차감 방식과 상관이 없었다.
- 정확한 방식에서는 5000건 중 4900건이 결제 없이 품절로 끝난다. 결제를 거친 요청은 많아야 100건이므로, p95 이상 걸린 약 250건(5000건의 5%) 가운데 최소 150건은 결제를 거치지 않은 요청이다.
- 즉 실행마다 결제 없는 짧은 경로의 요청이 최소 150건, 그 실행의 p95(구성별 중앙값 4.8~6.1초) 이상 걸렸다. 차감 서버 시간(≤ 53.38 ms)으로는 설명되지 않으므로, 대부분은 기다린 시간으로 보인다.
- 다만 order-service 안의 구간별 시간은 기록되지 않았다. 그래서 정확히 어디서 몇 초를 기다렸는지는 나눌 수 없다.

**order-service 가 왜 그만큼 DB 커넥션을 기다렸는지는 기록으로 나눌 수 없다.**
- 풀 크기(Hikari 기본값) 때문인지 MySQL 처리 시간 때문인지 가르려면 order-service DB 질의 시간이나 MySQL CPU 가 있어야 하는데, 기록되지 않았다.
- 다만 재고 행 락 경합이 원인이라는 근거는 없다. 락 대기가 적은 conditional(223회)과 많은 pessimistic(1969회)의 order Hikari pending 이 185와 183으로 같다.

**재고 쪽은 포화되지 않았다.**
- inventory Tomcat busy 최대는 중앙값 3~49로, 기본 최대 스레드 수 200에 크게 못 미친다. inventory Hikari pending 최대는 0~33이다.
- MySQL 현재 락 대기 수는 선택한 21회에서 많아야 9였다(1s 표본, `causes.json` 의 maxCurrentWaits).
- 표본 시점마다 한 행을 두고 동시에 기다린 요청은 한 자릿수였다.

**락 대기는 있었지만 짧았다.**
- pessimistic 은 락 대기 1969회(naive 557회의 3.5배), 평균 2.04 ms 였다.
- conditional 은 223회로 pessimistic 의 약 1/9 이지만, 평균 11.37 ms 로 한 번 기다릴 때 약 5.6배 길었다.
- 왜 이런 차이가 나는지는 기록된 지표로 설명할 수 없다.
- 실행별 누적 락 대기 시간(`lockTimeMs`)은 pessimistic 3195~4324 ms, conditional 1257~2654 ms 다. 5000건 전체를 합한 값이다.

**재시도는 재고 쪽 비용을 키웠지만 끝단에는 드러나지 않았다.**
- 재시도 총횟수는 r1 422, r2 625, r3 698이다.
- 같은 구간에서 차감 서버 p95 는 r0 3.63 ms → 16.84 / 53.38 / 41.59 ms, inventory Tomcat busy 최대는 6 → 49 / 4 / 49 가 됐다.
- 가장 크게 드러난 실행은 `20261102-225718-optimistic-r3` 다(inventory Hikari pending 124, Tomcat busy 135, 서버 p95 127.06 ms). 그런데 이 실행의 끝단 p95 4925.37 ms 는 r3 중앙값 그 자체다.
- 3회 사이 편차가 커서(r3 의 inventory Hikari pending 124 / 33 / 0, 서버 p95 는 r2 > r3) 재시도 횟수에 비례해 커진다고까지는 말할 수 없다.

**덜 팔림·타임아웃은 설명할 사슬이 없다.** 한 번도 나오지 않았기 때문이다.

## 4. 2단계로 넘어갈 근거

**이번 기록으로는 "DB 한 행에 몰리는 구조 자체의 한계"가 끝단 지연의 원인이라고 말할 수 없다.**
- 끝단 p95 4778~6118 ms 가운데 재고 차감 서버 시간은 2.41~53.38 ms(중앙값)로, 많아야 약 1%다.
- 재고 서비스는 포화되지 않았다(Tomcat busy 3~49, Hikari pending 0~33). 행 앞의 대기도 많아야 9건이었다.
- 같은 때 order-service 는 Tomcat 200/200, Hikari pending 182~189, gateway 는 Tomcat 195~200 으로, 방식과 무관하게 먼저 차 있었다.
- 따라서 pessimistic·conditional·r0 의 차감(2.41~3.63 ms)을 더 빠른 저장소로 옮겨도, 끝단 수 초에서 줄어들 몫은 작아 보인다.

**한 행 구조의 비용이 숫자로 남은 곳은 DB·재고 계층이다.**
- 낙관적 락 r0 에서는 5000건 중 505건(약 10%)이 충돌로 실패했다.
- 재시도로 r3 에서 186건까지 줄었지만, 차감 서버 p95 는 r0 의 약 11배(3.63 → 41.59 ms)가 됐다.
- pessimistic 은 차감 5000건에 락 대기 1969회를 냈다.
- 이 비용들은 실제로 있지만, 이번 조건에서는 앞단 포화에 가려 끝단까지 올라오지 않았다.

**정리하면 (판단은 사용자 몫):**
- 한 행 구조의 한계를 끝단 숫자로 보려면, 재고 쪽이 앞단보다 먼저 포화되는 조건이 필요하다.
- 그러려면 부하 규모나 고정 설정(Tomcat/Hikari 기본값)을 바꿔야 하는데, 둘 다 1단계 범위 밖이다.
- 지금 조건 그대로 2단계를 재면, 끝단 지표로는 1단계와 구분하기 어려울 수 있다(추정).
- 2단계로 갈 근거를 "한 행 경합"에 둘지, 다른 데에 둘지는 이 결과를 보고 정할 일이다.

## 측정 메모

- **1차 측정은 무효로 보관했다(`stage1-attempt1/`).** 2026-11-02 21:40~22:03 에 돌렸고, naive 외 18회 중 10회가 `INCONCLUSIVE` 였다(판매는 모두 100).
  원인은 직전 실행이 남긴 클라이언트 소켓 약 5000개가 호스트에 TIME_WAIT 로 남은 채 다음 k6 가 시작된 것이다. 요청이 연결 단계에서 실패했다.
  TIME_WAIT 5036개에서 시작한 실행은 `i/o timeout` 이 982건이었고, 49개에서 시작한 실행은 0건이었다. 이 기록의 수치는 비교에 쓰지 않았다.
- **대응:** `run-test.sh` 는 k6 시작 전에 호스트 TIME_WAIT 가 500개 미만이 될 때까지 기다린다. 기다린 시간과 시작 시 개수는 `meta.json` 의 `tcpDrainWaitSec`·`tcpTimeWaitBefore` 에 남는다.
  선택한 21회는 시작 시 29~227개, 대기 0~105초였다.
- **2차 측정에서 빠진 측정 4회:** 표 아래 목록의 4회는 `INCONCLUSIVE` 라 비교에서 뺐다.
  - k6 응답 중 분류되지 않은 연결 오류가 있었다(`k6-stdout.txt`).
    `20261102-224227-pessimistic` 314건과 `20261102-224622-conditional` 61건은 `connection reset by peer`, `20261102-225523-optimistic-r2` 548건과 `20261102-230324-conditional` 558건은 `i/o timeout` 이었다.
  - k6 → Docker Desktop 포트 포워딩 → gateway 연결 단계의 오류로, 요청이 order-service 에 닿지 않았다(주문 행도 주문 전 실패 기록도 없음). 재고 전략과는 무관하다. naive 워밍업(`20261102-221512-naive-warmup`)에서도 30건 났다.
  - `20261102-224227-pessimistic` 은 연결이 맺어진 지 약 15초 뒤에 reset 됐다(오류 22:43:11, 실행 시작 22:42:55, p95 ≈ 15000 ms). Docker Desktop 포트 포워더가 gateway 컨테이너를 포기한 것과 맞지만, gateway 의 accept 경로가 원인일 가능성은 배제하지 못했다.
  - 네 실행 모두 시작 시 TIME_WAIT 가 29~58개로 기준 아래였다. 그래서 TIME_WAIT 대기만으로는 사라지지 않았고, 더 깊은 원인은 좁히지 못했다. 네 실행 모두 판매는 100이었다.
  - 해당 구성은 워밍업 1회와 함께 다시 재서 대신했다. conditional 은 다시 잰 `20261102-230324-conditional` 도 `INCONCLUSIVE` 라 한 번 더 쟀다(`20261102-230645-conditional`).
- **환경:** 측정 중 같은 Docker VM(7.7 GiB)에 다른 프로젝트 컨테이너 7개가 유휴 상태로 함께 떠 있었다. 메모리 합은 약 1175 MiB 다(`stage1-environment.md`).
- **Prometheus 값:** Hikari·Tomcat·현재 락 대기·서버 p95 는 1s 표본이다. `20261102-221732-naive` 는 이 값들이 `n/a` 라, 표의 naive 해당 칸(`*`)은 나머지 2회로 계산했다.
