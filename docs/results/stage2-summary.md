# 2단계 요약: order-service 만 G1 GC(메모리 1g)로 바꾼 뒤 커넥션 대기 최댓값

> 이 실험의 order-service 설정(1g·G1)은 `feat/flash-sale-stage1` 의 `compose.yaml` 에 반영하지 않았다. 지금 order-service 는 640m·Serial GC 다.

질문은 **"order-service 의 커넥션 대기 최댓값이 줄어드나"** 였다.
1단계 4차에서 order-service 의 커넥션 대기 최댓값 3.74초가 Serial GC 의 Full GC 정지(3.27초)와 같은 초에 찍혔다.
그래서 order-service 만 컨테이너 메모리를 640m 에서 1g 로 올리고 `-XX:+UseG1GC` 를 줬다. 나머지 앱은 그대로(640m, Serial GC)다.
메모리를 올리면 최대 heap 도 448 MiB 에서 718 MiB 로 같이 커진다. 그래서 바뀐 것은 GC 종류와 heap 크기 두 가지다(사용자 결정).
조건은 1단계 4차와 같다. USERS 5000, 재고 100, 7개 구성마다 워밍업 1회와 측정 3회(2026-11-03 17:18~17:33). 환경은 `stage2-environment.md` 에 있다.

**한 줄 결론:**
- 워밍업을 포함한 28회 전체의 대기 최댓값은 **3,740ms → 1,014ms** 로 줄었다. order-service Full GC 는 1회(3,269ms) → 0회, GC 정지는 1초 표본 기준 최대 60ms 다.
- 측정 실행 구간의 대기 최댓값과 평균은 **그대로**다. 최댓값은 353~442ms → 304~685ms, 평균은 약 60ms 로 같다. 평소 대기는 커넥션 풀(10개) 앞 줄 서기에서 오고, GC 와는 관계가 없다.
- 1,014ms 는 첫 실행(naive 워밍업)에서 나왔다. 이때 Full GC 는 없었고 GC 정지는 최대 59ms 였다. 평균 대기가 178ms 로, 이후 실행(약 60ms)의 3배였다. JVM 이 덜 데워진 탓으로 보지만 확인하지는 않았다.
- 이와 별개로, 측정 21회 중 3회와 워밍업 1회에서 k6 요청이 60초 타임아웃에 걸렸다(1단계 4차는 0회). 그중 2회가 `INCONCLUSIVE` 다. 원인은 gateway 의 연결 대기열(100칸) 넘침으로 확인했다(§4).

## 1. 대기 최댓값

### 어떻게 쟀나

order-service 의 `hikaricp_connections_acquire_seconds_max` 는 Micrometer 가 최근 값만 남기는 감쇠 최댓값이다. 두 측정에서 관찰한 동작은 이렇다.
- 값은 60초마다 한 번씩 바뀐다(1단계 4차는 매분 48초, 2단계는 매분 53초).
- 한 번 찍힌 최댓값은 120~180초 동안 남는다.

그래서 이렇게 읽었다.
- 값이 올라간 시각(↑): 그 1초 안에 그만큼 기다린 획득이 있었다.
- 60초마다 바뀐 값: 직전 120초 동안의 최댓값이다.
- 실행은 약 10초 간격이라, 실행 하나의 최댓값은 따로 낼 수 없다. 그래서 `causes.json` 에는 평균 대기(카운터 차이)만 넣었다.

이 값은 실행 중인 Prometheus 에만 있어 스택을 내리면 사라진다. 그래서 아래에 옮겨 둔다(1초 간격 질의, KST).

## 2. 왜 평소 대기는 그대로인가

order-service 는 Tomcat 스레드 200개가 Hikari 커넥션 10개를 나눠 쓴다(둘 다 기본값). 주문 하나가 커넥션을 두 번 받는다.
두 측정 모두 order Hikari pending 최댓값이 181~186 이다. 커넥션 하나를 받으려면 그 앞의 약 185개가 먼저 받고 돌려줘야 한다.
커넥션을 쥐는 시간은 평균 3.33ms(4차)와 3.47ms(2단계)로 거의 같다. 10개가 돌아가며 비니 하나가 비는 간격은 약 0.33~0.35ms 이고, 185 × 0.33ms ≈ 61ms 로 평균 대기와 맞는다.
이 줄은 GC 를 바꿔도 그대로다. Full GC 는 이 줄 전체를 정지 시간만큼 더 세워 두는 일이었고, 1단계 4차에서는 워밍업 때 한 번 일어났다.
Serial GC 에서는 Old 영역(약 299 MiB)이 차서 Full GC 가 났다. G1 에서는 heap 사용량이 최대 191 MiB 에 머물러 Full GC 까지 가지 않았다.
바뀐 것이 GC 종류와 heap 크기 두 가지라, 어느 쪽 덕분인지는 이 측정으로 가를 수 없다.

원인은 따로 조사해 확인했다(`stage2-gateway-diagnosis/README.md`).
- **원인은 게이트웨이의 연결 대기열(Tomcat `accept-count` 기본값 100칸)이다.** 연결 5000개가 같은 순간에 몰리면 대기열이 넘친다.
- 넘쳐 버려진 연결은 클라이언트가 재전송한다. 재전송 시점이 6.2·12.6·25.4·51.0초에 한꺼번에 몰리고, 그때마다 약 100~200건만 들어간다.
- 51초에도 못 들어간 요청은 다음 재전송이 약 102초 뒤라 k6 60초 타임아웃에 걸린다. 주문이 없고 504 도 없는 이유다.
- 게이트웨이를 바꿔 본 진단 실행(군마다 8회)의 결과는 이렇다.
  - swap 만 없앴을 때: 늘어진 실행이 남았다.
  - 대기열만 4096칸으로 늘렸을 때: 넘침과 늘어짐이 사라졌다.
- 게이트웨이는 별개로 swap 을 쓴다. 640m 한도에 JVM 이 약 800 MiB 를 쓴다. 그래서 GC 가 0.4~1.8초씩 멈춘다. 이 정지는 지연을 키우지만 타임아웃의 원인은 아니다.
- 실행마다 결과가 다른 것은 첫 몰림의 넘침 양(0~16,850건)이 흔들리기 때문이다. 2단계가 4차보다 많았던 이유는 정하지 못했다.

1단계 4차의 155008-conditional 도 같은 모양(응답 대기 최대 52.5초)이었으므로, order-service 변경 때문에 생긴 문제는 아니다. 대기열 크기·게이트웨이 메모리는 고정 설정이라 이번 단계에서는 바꾸지 않았다.

## 5. 한계

- 실행 하나의 대기 최댓값은 현재 지표로 낼 수 없다. 120초 창 최댓값이 최선이다.
  정확히 재려면 Micrometer 감쇠 시간을 줄이거나 히스토그램을 켜야 한다. 이는 앱 설정 변경이라 하지 않았다.
- 2단계 매트릭스는 4차보다 덜 데워진 JVM 에서 시작했다. 4차에는 매트릭스 전 USERS 5000 사전 확인 실행이 있었다.
- 측정 중 `docker stats` 표본을 2초마다 떴다. 4차에도 k6 컨테이너 표본을 떴다.
